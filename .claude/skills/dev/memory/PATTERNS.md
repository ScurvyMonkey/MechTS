# Patterns

### [2026-09-09] — Dev — Terrain Detail Mesh prototypes are pure data, no code path (issue #88)
**Context:** Registered the remaining 17 of 20 vegetation prefabs as `TerrainData.detailPrototypes` entries on `OutdoorTerrainData`.
**Learning:** This is 100% Editor-time `TerrainData` asset content (`DetailPrototype` struct array) — no ScriptableObject, no MonoBehaviour, nothing in `Assets/Scripts/` reads or references it. `DetailPrototype`'s C# default constructor already matches the `healthyColor`/`dryColor`/`targetCoverage` values the 3 pre-existing hand-configured entries had (confirmed by reading both back) — don't bother explicitly setting those fields to "match convention," the defaults already do. Only `minWidth`/`maxWidth`/`minHeight`/`maxHeight` (and `usePrototypeMesh`/`useInstancing`/`renderMode`/`noiseSpread`/`useDensityScaling`, which do differ from C# defaults) needed explicit values.
**Apply when:** Any future Terrain Detail Mesh (or other `TerrainData` sub-asset) work in this project — check the live asset's actual field values via `unity-mcp` before assuming what "matching the existing convention" requires; some fields may already be free via the API's own defaults.

### [2026-09-09] — Dev — An arch-approved NavMesh exclusion plan broke on first real test (issue #89)
**Context:** Retiring `Ground` in favor of `OutdoorTerrain` as the real gameplay surface. The arch review's plan included excluding `OutdoorTerrain` from the Flying agent type's NavMesh bake, mirroring the existing `Platform_Tier1`/`Ramp` exclusion (issue #40) — sound-looking reasoning by analogy (flying should bypass elevation the same way it bypasses a platform).
**Learning:** Implemented exactly as planned, baked, and directly tested with `NavMesh.SamplePosition` — and it broke Flying's NavMesh completely (zero walkable area anywhere, not just near elevation). The analogy to `Platform_Tier1`/`Ramp` was structurally wrong: those are small, isolated obstacles sitting *on top of* an always-present flat surface (`Ground`), so excluding them restores a real fallback underneath. `OutdoorTerrain` *is* the surface itself — with `Ground` also gone (this same issue's own change), excluding it left nothing to fall back to. The plan read as correct on paper (same exclusion mechanism, same stated goal) but the actual geometry relationship it depended on didn't hold. Caught only because the empirical test (`NavMesh.SamplePosition` at the flat map origin, not just near the change's own focal point) was run before declaring it done — a narrower test (only checking near the sculpted peak) would have looked like a pass.
**Apply when:** Implementing an arch-approved plan that extends an existing pattern by analogy (`X` worked for case `A`, so apply `X` to case `B` too) — verify the actual structural assumption the original pattern depended on still holds for the new case, not just that the same code shape applies. And when testing a fix, sample at a point *unrelated* to the specific bug you're fixing (e.g. the flat map origin, not just the sculpted peak) — a regression that breaks everything can hide behind a test that only re-checks the original symptom.

### [2026-09-10] — Dev — Verifying a private EditorWindow method by mirroring, plus testing the real public dependency directly (issue #94)
**Context:** `MapShellGenerator.Generate` and its helper methods are private instance methods on an `EditorWindow` — this project has repeatedly confirmed (issues #56/#63/#71) there's no reliable reflection-invoke path for `EditorWindow` private methods in its `unity-mcp` sessions.
**Learning:** Split verification into two parts rather than trying to force one approach to cover everything: (1) the one real, reusable production dependency the new code calls into — `MapEditorPainter.TryPaint` (public) — was tested directly and for real, with a deliberately-wrong input Y to prove the Y-force fix actually overrides it correctly; (2) the new private generation math (noise, blending, rejection-sampling) was verified by mirroring the exact algorithm in a `RunCommand` script run against the real scene and real config asset, since that's the only way to exercise this project's private `EditorWindow` logic at all. The mirror still called the real `TryPaint` for placement, not a mocked version, so the placement half of the test was never mirrored.
**Apply when:** Verifying any future private `EditorWindow` logic — identify which parts of the new code call into an existing *public* dependency (test that directly, for real) versus which parts are genuinely new private logic (mirror only that part, exactly, against real project data) — don't mirror more than necessary just because reflection is unavailable.

### [2026-09-10] — Dev — Naive offset placement can't auto-align modular kit pieces (issue #95)
**Context:** Issue #94's Map Shell Generator placed a `Ramp` next to each generated `Platform_Tier1` via a fixed XZ offset (`platformSpacing * 0.3f` along X, no rotation) — the same shape as every other procedural placement in that tool (random position + minimum-spacing rejection sampling).
**Learning:** This worked fine for foliage (any position/rotation looks like a reasonable tree) but produced a visibly broken result for `Platform_Tier1`/`Ramp` — real designer usage showed the ramp sitting at a random angle, never actually connecting to the platform edge. Modular kit pieces meant for precise, edge-to-edge hand-placement (this project's own `Platform_Tier1`/`Ramp`, and by extension `SpacePlatformKit`'s grid-snapping pieces) can't be auto-placed with a generic "random position, minimum spacing" approach the way loose/organic content (trees, rocks, resource clusters) can — connecting them correctly needs real geometry-aware logic (matching footprint dimensions, choosing a rotation that actually faces the right edge), which didn't exist and wasn't built. Removed the feature entirely rather than leaving a half-working version in place.
**Apply when:** Considering procedural/automatic placement for any modular, edge-connecting kit piece in this project (`Platform_Tier1`/`Ramp`, `SpacePlatformKit`'s walls/platforms/connectors) — a random-position-plus-spacing approach that works fine for organic scatter content will not produce a usable result for these; don't reuse that pattern without first designing real alignment logic, or scope it out like this issue did.

### [2026-09-11] — Dev — Two more real findings wiring up pack fire animations (issue #91)
**Context:** Adding a shared `WeaponFireAnimator` (mirroring `HarvesterPartAnimator`'s `Animator.enabled` toggle) to Ranger/Reaper/the Machine Gun Turret.
**Learning:** (1) The spec/arch review assumed "one Animator per unit," but direct hierarchy inspection found `BattleDroidBlue`'s model has **two** independently-animated gun arms (`LowerArm_L/MinigunBlue` and `LowerArm_R/MinigunBlue`, each its own `Animator`) — the component needed a `Animator[]` array, not a single reference, discovered only by inspecting the actual prefab hierarchy rather than assuming "one weapon, one Animator." (2) `SendMessage`-invoking a component's own `Update()` in this project's frozen-player-loop `unity-mcp` sessions *does* let `Time.deltaTime` decay a timer correctly (it consistently reports `~0.02`, Unity's default fixed timestep, even with `Time.frameCount` stuck) — confirmed directly by forcing 20 ticks and watching a 0.3s window correctly expire. This is a genuinely useful verification technique for timer-based gating logic that the existing `HarvesterPartAnimator` precedent didn't need (its own gate is a plain boolean, not a decaying window). Calling `Animator.Play()`/`Animator.Update(0f)` this way (real engine animation frames never actually ran in between) does produce benign `Animator`-internal warnings ("not playing an AnimatorController", "object is inactive") — no exceptions, matching the exact accepted bar `HarvesterPartAnimator`'s own verification history already established for this class of artificial-tick limitation.
**Apply when:** Wiring any future pack-sourced weapon/part animation — check the actual prefab hierarchy for how many `Animator`s exist before assuming one; matched-parts rigs (dual arms, dual thrusters, etc.) are common in these packs. And when a new gating component needs real elapsed-time behavior (a decay timer, not just a boolean toggle) in a frozen-loop session, `SendMessage("Update", ...)` in a loop is a valid way to drive it — `Time.deltaTime` reports a real, usable value even when `Time.frameCount` never advances.
