# Decisions

### [2026-09-09] — Arch — Terrain elevation: retire Ground, Terrain becomes the real surface (issue #89)
**Context:** Issue #89 ("Playable Terrain Elevation via Terrain Tools") asked whether `Ground` (the flat invisible Y=0 gameplay/raycast plane) or `OutdoorTerrain` (the sculptable Terrain component) should be the source of truth once real elevation is wanted everywhere.
**Learning:** Decided: `Ground` is retired; every `_groundLayerMask`-typed raycast (`SelectionController`, `AttackCommand`+`OrderResolvers/`, `BuildingPlacement`, `MapEditorPainter`/`Preview`/`Window`) retargets to the `Environment` layer (`OutdoorTerrain`'s own `TerrainCollider`, already present since issue #84's correction). This was verified, not guessed: `NavMeshBuilder.CollectSources` already treats `OutdoorTerrain` as a real `NavMeshBuildSourceShape.Terrain` source with zero code changes (confirmed live), so the only real gaps were (a) `NavMeshBakeUtility`'s Flying-agent exclusion only covers the Map Editor's `MapContent/Terrain` category, not `OutdoorTerrain` itself, and (b) every gameplay raycast still targets `Ground`, which stays flat regardless of sculpting — confirmed as an already-live inconsistency (a test stamp on `OutdoorTerrainData` reaches world Y≈3.04, already baked into `NavMesh.asset`, while every `Ground`-layer raycast at that same XZ still resolves Y≈0).
**Apply when:** Any future work touching terrain elevation, the `Ground` GameObject, or any `_groundLayerMask` field — `Ground` is being phased out as the gameplay surface in favor of Terrain's `Environment` layer. Don't reintroduce a flat-plane assumption once issue #89's implementation lands. Also apply generally: `NavMeshBuilder.CollectSources` in this project's `NavMeshBakeUtility.cs` already natively sources `Terrain` components marked `NavigationStatic` — don't assume Terrain needs special-casing to contribute to a NavMesh bake, it already does.
