# BA — Requirements Mapping History

### [2026-09-09] — BA — Terrain Tools adoption ("everything stampable")
**Context:** Designer asked for "everything stampable," said they'd "started creating detail meshes," and wanted a Terrain Tools cheat sheet.
**Learning:** The literal request pointed at Stamp Terrain's Mesh mode (imprinting a mesh into the heightmap) and implied new custom meshes had been authored. Neither was true: checking the project (no new .fbx/.obj/.blend files anywhere, `git status` clean of new mesh assets) and then asking directly revealed the designer had used Terrain's native **Paint Details** system — clicking "Add Detail Mesh" in the Terrain Inspector and registering existing Terrain Sample Asset Pack prefabs (`Grass_A`, `Bush_A`, `Fern_A`) as scatter objects. "Stamp" was used loosely for "any click-to-place terrain-authoring action," and "detail meshes I created" meant "Detail Mesh *entries* I added," not new geometry.
**Apply when:** A designer describes their own Unity/tool usage in casual terms — verify against actual project/asset state via `unity-mcp` (query the live TerrainData, check for new files) before scoping a spec, rather than taking the terminology at face value. This project in particular has enough Terrain-adjacent systems (Stamp Terrain, Paint Details, Mesh Stamp, the Map Editor's own brush system) that similarly-named-but-different mechanisms are easy to conflate. See [[design-profile-terrain-scope]].

### [2026-09-11] — BA — "Black rendering" bug report, misdiagnosed hypothesis (issues #97/#98)
**Context:** Designer reported "black rendering" when manually lowering terrain elevation, and guessed the cause: "Maybe we layer the resources and buildings units to be a layer above the terrain so they always sit on top?"
**Learning:** The designer's own hypothesis was wrong, but the underlying observation ("it is eating the resources") was a real, valuable symptom pointing at the actual bug from a different angle. Root cause (found via direct `unity-mcp` investigation before drafting any spec — ruled out terrain-data corruption first, then traced it to `FogOfWarRenderer`'s flat shroud quad no longer being occluded by terrain wherever elevation dropped at/below its fixed `Y=0.05` height) had nothing to do with render-layering between resources/buildings and terrain — it was a fog-of-war rendering system built for a flat world, never updated after terrain gained real elevation (issues #84/#89/#94). The designer accepted the corrected diagnosis without pushback once shown the investigation, and picked the more thorough/correct fix (terrain-conforming mesh) over the simpler one (raise the flat plane) when the tradeoff was explained.
**Apply when:** A bug report arrives with the reporter's own causal hypothesis attached — investigate the actual mechanism directly (this project's `unity-mcp` access makes that cheap) before accepting or building around their guess; a wrong hypothesis doesn't mean the reported symptom isn't real or valuable, just that the *explanation* needs independent verification. Also: this session surfaced two related-but-separable asks (a bug + a feature) from one casual message — split into two issues per this designer's established preference for separate issues along natural seams (see [[requirements-fire-animation-split]] equivalent entry in DESIGN_PROFILE.md), sequencing noted in each issue body rather than blocking one on the other formally.
