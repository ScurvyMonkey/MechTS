# BA — Designer Profile

### [2026-09-09] — Scope ambition & precedent-revisiting {#design-profile-terrain-scope}
**Context:** CLAUDE.md documents `OutdoorTerrain` (issue #84) as a deliberate, explicitly-decided "purely visual backdrop, deliberately kept flat" — a real architectural precedent, not a placeholder. When asked directly whether new terrain sculpting should stay backdrop-only or become real playable elevation, the designer chose the latter without hesitation ("Terrain sculpting should include everything... we may need to add this as a bake step") — correctly anticipating the NavMesh implication himself.
**Learning:** This designer is comfortable overturning a previously-shipped architectural decision once a better tool/idea comes along, and thinks ahead to real technical consequences (the NavMesh bake step) rather than just asking for the visual outcome. Don't assume an existing CLAUDE.md precedent constrains the ceiling of a new ask — surface it as context and ask directly rather than pre-narrowing scope to match past decisions.
**Apply when:** Speccing any feature that touches previously "decided" architecture in this project — state the existing precedent plainly, then ask rather than assume it should hold. Also: this designer's requests tend to arrive slightly under-specified/terminology-loose (see [[requirements-terrain-tools-scope]]) but the actual intent, once drawn out, tends toward the more ambitious/complete option ("everything") over the conservative one.

### [2026-09-09] — Prefers separate issues over one bundled spec when work has natural seams
**Context:** A single investigation (unused pack animations across the roster) turned up 7 findings splitting cleanly into 3 groups by shared gating mechanism (weapon-fire, production-queue, disabled-aware-continuous). Offered as one combined spec; the designer asked to split it into separate issues instead, with no further guidance on where the lines should be.
**Learning:** Given a bundled spec whose findings already have a natural grouping, this designer wants that grouping surfaced as separate issues rather than one large one — even though the underlying investigation and pattern (gate `Animator.enabled` on existing state, matching `HarvesterPartAnimator`) is identical across all of them. Splitting along "what state each group is gated on" (rather than e.g. splitting by unit vs. building) produced clean, independently-shippable issues with no cross-issue dependency.
**Apply when:** A `/ba` spec covers multiple findings/items from one investigation — proactively note the natural split points in the spec itself (as this session did in "Affected Systems") so a later "split it" request has an obvious answer ready, rather than needing to re-derive groupings from scratch.

### [2026-09-10] — Accepts scoped-down recommended defaults readily, when the reasoning is shown
**Context:** Pitched a Procedural Map Shell Generator. Three real scope forks existed (generate gameplay placement too vs. terrain-only, multiple named presets vs. one tunable generator, symmetry support vs. none) — each offered as a batched multiple-choice question with a "(Recommended)" option and a one-line reason for the smaller/simpler scope each time. The designer accepted all three recommended (smaller-scope) answers without pushback or modification.
**Learning:** This is the opposite pull from [[design-profile-terrain-scope]]'s "tends toward the ambitious/complete option" — but the two aren't actually in tension: that entry was about an *open* question ("should this stay backdrop-only or include everything?") where the designer supplied the ambition himself. Here, three *closed*, pre-reasoned multiple-choice questions were asked, each already narrowing toward the simplest defensible v1 scope with the "why" stated up front — and the designer deferred to that framing every time. This designer isn't reflexively maximalist; he scales ambition to match how the question is posed.
**Apply when:** Scoping a genuinely new, open-ended system (not a "should this feature already do X too" question) — a batched, reasoned multiple-choice with clear recommended defaults is an efficient, low-friction way to pin down scope quickly, and this designer will generally accept the smaller/simpler recommended option rather than push for maximal scope, as long as the reasoning for the smaller scope is actually shown, not just asserted.
