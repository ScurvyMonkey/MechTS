# Design Profile — Drew (MechTS)

- Iterates via a scratch `docs/Requirements.md` file — dumps rough, unordered feature thoughts there for `/ba` to review and convert into real specs. Treat that file as raw input, not a spec; expect it to contain items spanning multiple future issues at once.
- Answers structured multiple-choice questions (via AskUserQuestion) quickly and decisively — comfortable resolving several open questions in one batch when they're laid out as concrete options with a recommended default.
- Comfortable with big systems being broken into a sequence of issue-sized specs (e.g. state machine scaffolding → economy → espionage → battle) rather than one mega-issue. Confirmed this breakdown without pushback on the first core-loop spec — default to proposing sequenced, dependency-ordered issues for large systems.
- GDD "pitch" language (e.g. "ships with a full campaign, multiplayer, and co-op mode") does not necessarily mean immediate build scope — see [[requirements-vs-spec]]. Always check pitch-level GDD statements against `CLAUDE.md`'s phase roadmap rather than taking them as a scope commitment.
- Sometimes writes raw design notes directly into `docs/GDD.md` between `/ba` sessions (not only into the `Requirements.md` scratch file) — confirmed 2026-08-19 when a "Technology Upgrade Trees" section with real design detail (per-faction trees, a `Gun -> Gun Level 1 -> Gun Level 2` tiering example) turned up in the GDD mid-spec, unmentioned in the conversation and contradicting an assumption already drafted into a pushed issue. Always read `docs/GDD.md` in full before/while drafting a spec, not just its "What's Actually Decided"/"What's Not Decided Yet" summary lists — a designer note living in a later section of the file can already answer something the summary lists as open, or override an assumption the current spec is quietly making.
- When Drew flags genuine implementation-approach uncertainty ("not sure if this is done with X or Y, my guess is Z") rather than a pure design question, it's worth actually researching the technical landscape before presenting options back — for the Map Editor request ("not sure if Tilemaps or hybrid prefab+tilemap"), checking what Unity already ships (a built-in Tile Palette tool) changed the recommended approach entirely (adopt the stock tool for terrain, reserve custom code for the part Unity has no equivalent for) rather than just asking Drew to pick between his own two guesses. Confirmed 2026-08-19 — the researched recommendation was accepted immediately.
- References other RTS games directly as a design shorthand (e.g. "similar to SC2" for camera saved-locations) rather than describing the mechanic from scratch — when this happens, it's usually precise enough to propose the exact real-game binding/behavior back as a concrete recommended option (via AskUserQuestion) rather than asking an open-ended follow-up. Confirmed 2026-08-19 (Camera Manager spec, issue #10): proposing "F1-F4 jump / Ctrl+F1-F4 save, exact SC2 scheme" was accepted immediately as the recommended option.
- Has screenshots ready for UI/visual complaints in `Requirements.md` and will share one the moment it's asked for, even when the written description alone reads as a design/positioning question. Confirmed 2026-08-20 (HUD Layout Rework, issue #19): "add Selection info into the control-groups canvas" read like a corner-relocation request, but the screenshot revealed it was actually describing a rendering bug (`SelectionPanel`'s text/indicators rendering outside their own background box). Ask for a screenshot early on any UI-positioning complaint before drafting acceptance criteria around a design guess — it can turn a "where should this go" question into a precise bug diagnosis instead.
- Doesn't reflexively pick the "Recommended" option in scoping questions — will choose the higher-scope alternative when it matches genuine genre expectations. Confirmed 2026-08-20/21 (Unit Orders, issue #26): chose "multi-point patrol loop" over the recommended simpler two-point back-and-forth, right after declining the equivalent higher-scope option (multi-waypoint rally path) for Rally Points (#23) earlier the same session. Don't read "Recommended" as a prediction of what he'll pick — each scoping question is independent, and he's evaluating against what a real RTS player would expect for *that specific feature*, not defaulting to whichever costs less to build.
- Comfortable with rapid-fire sequential `/ba` sessions across an entire backlog in one sitting ("continue specing out the remaining requirements" for "the remaining of the night") — pushed 5 issues (#23-#27) back to back with minimal per-issue back-and-forth once genuine ambiguities were resolved via AskUserQuestion. Don't throttle pacing or add extra confirmation checkpoints beyond presenting each finished spec; keep moving to the next backlog item once one is pushed.
- Actively revises shipped decisions after seeing them in real play, not just at spec time — see [[requirements-vs-spec]]'s 2026-08-21 entry (reversed issue #20's main-building-invulnerability one session after it shipped). Keeps adding to `docs/Requirements.md` between sessions rather than treating a closed issue as the final word — always re-read the current file in full at the start of every `/ba` session, don't rely on memory of what it said last time.
- Wants `docs/Requirements.md` actively curated, not just appended to — confirmed 2026-08-23: asked to compact every implemented line down to its GitHub issue number so the file stays a legible live backlog instead of accumulating stale, already-shipped requirement text alongside open ones. Treat this as standing process going forward (see [[requirements-vs-spec]]'s same-day entry), not a one-off cleanup — fold newly-shipped items into the Implemented section as part of normal spec-pushing.
- When told to proceed through a list "in your suggested order," takes that as authorization to just go — pushed straight to drafting/pushing the next spec without re-confirming priority again. Don't re-ask "should we do X next" once he's already agreed to an ordering; move directly to drafting.
- Proposes entire multi-system sequences unprompted, at a conceptual/exploratory level, before any single piece is spec'd — confirmed 2026-08-24: laid out a full 5-part hybrid economy redesign (upkeep, area-based nodes, an auto-gather building, a Battle-Round-locked pool, an "Injection Round") in one message, expecting `/ba` to help decompose it into a dependency-ordered sequence rather than presenting one issue-sized idea at a time. Comfortable working top-down from vision to sequenced issues in the same conversation.
- Designs forward-compatibly for Phase 2 (co-op Commander/General) without expecting it built now — confirmed 2026-08-24 (Injection Round): used language describing two roles "agreeing," which read as assuming live co-op was in scope; when asked directly, clarified he wants the *mechanic* shaped for the future split but fully playable/buildable solo in Phase 1 now, no networking implied. Don't read future-multiplayer-shaped language as a scope-creep mistake — ask plainly whether it's forward-compatible-solo-now vs. an actual Phase 2 ask; he'll answer directly either way.
- Refinement to the "doesn't reflexively pick Recommended" note above: across the entire 2026-08-26/27 hybrid-economy + resistances speccing arc (Auto-Extractor, Locked Pool, Injection Round, its Battle-Round correction, Weapon-Type Resistances — roughly 15+ AskUserQuestion rounds), he picked the Recommended option essentially every time. The one exception (Locked Pool's "pool relationship" question) was him rejecting both *offered* options for a third, more concrete one he'd already half-designed — not picking the non-recommended option from the pair. Cross-referencing the earlier confirmed cases of picking higher-scope non-recommended options (Patrol's multi-waypoint loop, Rally Points' path) — those were all **gameplay-feel** questions (what should this feel like to play, matching real RTS-player expectations). The technical/implementation-shape questions (how should this work under the hood — round-structure, funding-source mechanics, revert semantics, damage-type modeling) get Recommended accepted reliably. When drafting a batch of clarifying questions, expect gameplay-feel ones to have real odds of the higher-scope pick; expect mechanism/architecture ones to land on Recommended almost every time.
- When presented with two draft scoping options for a vague mechanic, may reject both in favor of a third, more concrete mechanic he'd already half-designed in his head (usually building/structure-based) — confirmed 2026-08-26 (Locked Resource Pool, issue #52): neither offered option ("separate pool" vs. "redirected income") matched his actual answer, a physical Silo building plus a player-set allocation-% menu. See [[requirements-vs-spec]]'s same-day entry. Don't treat a rejected pair of options as a dead end — immediately re-draft clarifying questions around whatever concrete mechanic he introduces instead.
- Deliberately embraces "no safety net" mechanics as strategic depth rather than guarding against them — confirmed 2026-08-24 (issue #48, upkeep): when asked whether a negative stockpile should clamp to zero at the Economy→Battle Round transition (so it never blocks Battle Round production), he rejected the clamp outright — a negative carryover is the intended cost of an all-in strategy (explicitly framed via SC's Zergling-rush/mass-army archetype: sacrifice late-flexibility for a bigger army now). Don't default to "add a safety clamp/guard rail" recommendations for this designer without checking whether the harsh consequence is actually the intended strategic tension first — he consistently prefers real, meaningful tradeoffs over softened ones once a mechanic's stakes are made explicit to him.
- **2D was always a bootstrapping choice, not the real destination — 3D was the original intent from before project setup.** Confirmed 2026-08-29 when Drew opened a feasibility request on five 3D SciFi RTS asset packs with "It was always my attention to make this a 3D game but getting mechanics set up is always easier in 2D." This directly contradicts `docs/GDD.md` line 24's documented "Engine/tech: Unity 6, URP 2D" — the single biggest instance yet of a "decided" fact in the docs turning out to be provisional (see [[requirements-vs-spec]]'s same-day entry). Apply forward: don't treat the 2D sprite pipeline / flattening convention / orthographic top-down camera as this project's permanent identity in future sessions — it's the current phase of a project explicitly headed toward 3D, and more pivot-shaped requests (camera angle, roster conversion, lighting) should be expected, not treated as scope-creep surprises each time.
- When a technical/architecture-shape fork is framed as "prototype small and validate before committing" vs. "commit to the bigger version now," Drew picks the validate-first option — confirmed 2026-08-29 (3D pipeline camera-angle question, first round): chose "prototype-first, decide after seeing it" over committing to an angled camera immediately, consistent with the already-established pattern that mechanism/architecture questions (not gameplay-feel ones) land on the Recommended option reliably.
- **Follow-up confirming the gameplay-feel-vs-mechanism split once more, same session:** once the #64 prototype actually rendered real 3D models, Drew was asked the *same* camera-angle question again with real evidence in hand — and this time picked "angle the camera now" (the higher-cost, non-recommended option) over keeping the technically-safer top-down view, right alongside picking the Recommended "one vertical slice first" answer for the separate rollout-scope question in the same batch. Camera angle is a visual-identity/gameplay-feel call (what should the game look like), not an architecture-mechanism call (how should this be built) — reinforces that the split isn't about "has this been asked before," it's about which *kind* of question it is. Expect this pattern to keep holding: feel/identity questions are genuinely up for grabs even after Drew's picked the cautious option on a related mechanism question moments earlier.
- **Opens a big system by stating the full long-term vision first, then explicitly narrowing to a small near-term ask himself** — confirmed 2026-09-01 (Enemy AI): described the eventual system in genre terms ("adaptive to player skill," "scalable difficulty," "build orders... simulating possibilities") but immediately flagged the hardest piece ("this is a much later system") and named the actual near-term deliverable ("right now harvesters completed... have them begin harvesting"), plus the process he wants going forward (validate a player unit, then build its AI equivalent, per unit type, staggered). Don't scope the vision-level language into the current issue — take the self-narrowing at face value and spec only the piece he named as "right now," logging the rest as flagged future direction (see [[requirements-vs-spec]]'s same-day entry). All three architecture/mechanism AskUserQuestion forks in that same session landed on Recommended — a fourth confirmation of the gameplay-feel-vs-mechanism split above.
- **Confirms the gameplay-feel-vs-mechanism split a fifth time, with a new "ship now, iterate" data point** — confirmed 2026-09-02 (Angled Perspective Camera, issue #80): picked Recommended ("True Perspective") on the pure mechanism question (Orthographic-tilted vs. real Perspective), then picked the non-recommended "accept the rough look for now" over both "add sprite billboarding" (a cheap, Recommended-marked stopgap) and "defer the camera change" when told most of the current roster is still flat 2D sprites that will look foreshortened/rough under the new angle. This is squarely the same "deliberately embraces no-safety-net tradeoffs, prefers shipping and iterating over guarding against a known-rough interim state" instinct already logged for issue #48's upkeep-negative-stockpile decision — don't propose a defensive/stopgap option as if it's the safe default for this designer; he'll often take the direct hit and move on rather than spend engineering effort softening a temporary rough edge.
