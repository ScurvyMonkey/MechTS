# Requirements → Spec deltas

### 2026-08-17 — BA — Game State Machine Scaffolding (issue #1)
**Context:** First `/ba` session on the Economy/Battle Round core loop. GDD Overview stated the game "ships with a full campaign, multiplayer, and a co-op mode" (Commander/General split), and Requirements.md listed "Players: Single player, Co-op Versus, PvP."
**Learning:** This read like a Phase 1 scope expansion, but when flagged against `CLAUDE.md`'s roadmap (Phase 1 = single-player campaign only, Versus is Phase 2 "way down the road"), Drew confirmed the roadmap stays as-is — multiplayer/co-op is documented future vision in the GDD, not something to plan the Phase 1 architecture around yet. See [[design-profile]].
**Apply when:** A GDD "Overview" or pitch-level statement describes a bigger scope than `CLAUDE.md`'s current phase. Don't infer expanded build scope from pitch language — flag it explicitly and confirm against the roadmap before specing anything phase-2-shaped as if it were near-term.

### 2026-08-17 — BA — Economy Round espionage mechanic
**Context:** GDD described Economy Round "attacks" narratively as spies/engineers/terrorists causing "economical damage" to the opponent, phrased ambiguously enough to read as either direct unit control or an abstracted targeted ability.
**Learning:** Drew confirmed it's direct real-time unit control (same input model as any other unit), just restricted to economic targets. Narrative/flavor descriptions of RTS mechanics in this project tend to mean full unit control even when phrased as an abstract "action," not a simplified ability-click.
**Apply when:** A GDD or Requirements.md entry describes a mechanic narratively (flavor-first) rather than mechanically — don't assume the simpler/abstracted implementation; ask rather than guess which one is meant.

### 2026-08-17 — BA — Economy Round: enemy runs a parallel economy
**Context:** Drafting the Economy Round resources/production spec (issue #2), it wasn't clear whether the Aliens enemy faction has its own Economy Round or just a pre-authored Battle Round force per mission.
**Learning:** Drew confirmed the enemy does run its own parallel Economy Round. This meant the spec's data model had to change from "single player economy" to "per-faction economy" (stockpiles, main building, nodes all keyed by faction) even though this is still single-player Phase 1 — the *opponent* is AI-driven but structurally symmetric to the player, not a scripted/static force. The AI's actual decision-making logic was kept as a separate future issue; this issue only had to make the systems faction-agnostic.
**Apply when:** Specing Economy or Battle Round systems — default to a per-faction/per-player data model (even in single-player-vs-AI missions) rather than a single implicit "the player's" economy, since the enemy is a full economic actor, not just a battle-round obstacle.

### 2026-08-17 — BA — Production doesn't fully lock out at Battle Round transition
**Context:** Issue #2's acceptance criteria said ALL economy actions, including "production," stop the instant Battle Round begins. Drafting the Battle Round spec surfaced a contradiction: the GDD's Battle Round section says the player "can build units to complete the mission," meaning unit production from Economy-Round-placed production buildings continues into Battle Round, funded by leftover resources — only harvesting and new economic/infrastructure building placement actually lock out.
**Learning:** A round-boundary rule stated in general terms ("economy actions stop") can be wrong in a way that only surfaces once the *next* round's spec is drafted against it. Drew confirmed the correction readily and was fine amending an already-pushed issue (#2) rather than treating it as settled once created.
**Apply when:** Drafting a spec for round N+1, re-check round N's "what stops/locks out" acceptance criteria against it — don't assume an already-pushed issue's boundary conditions are correct just because they were confirmed at the time. It's normal and expected to go back and edit a merged/pushed issue when a later spec reveals an inconsistency; use `gh issue edit` + a comment explaining the correction, don't silently diverge.

### 2026-08-17 — BA — Foundational systems can surface after the issues that assumed them
**Context:** Issues #2 (Harvester) and #3 (Saboteur) were both drafted and pushed referencing single-unit direct control and a `Units/` folder convention, implicitly assuming a `UnitBase`/selection/command system existed. It didn't — that foundation only got spec'd as issue #4, once Battle Round's need for full-army control made the gap obvious.
**Learning:** On a project built via sequential `/ba` sessions (not a single upfront architecture pass), it's normal for a foundational system to get identified *after* content issues that depend on it already exist, because the need for the foundation isn't obvious until a later feature needs it at scale (one Harvester's direct control doesn't demand a real selection system; a Battle Round army does). Drew was comfortable with this — the fix was calling it out explicitly (issue #4 numbered after #2/#3 but flagged as a dependency they should retroactively build on), not going back to renumber or block on re-sequencing.
**Apply when:** A new spec needs a system that an earlier, already-pushed issue quietly assumed — call out the dependency direction explicitly in the new issue (which existing issues should integrate with it) rather than either blocking the new spec on renumbering or silently duplicating the foundation piecemeal per-issue.

### 2026-08-17 — BA — Full core loop spec'd: issues #1–6
**Context:** First full `/ba` pass on the Economy Round / Battle Round core loop, working from a freshly-detailed GDD + Requirements.md dump.
**Learning:** The core loop ended up as six sequenced issues, not the original four: #1 Game State Machine, #2 Economy Round (Resources & Production, later corrected for production carryover), #3 Espionage (Saboteur), #4 Unit Selection & Command Foundation, #5 Combat Resolution, #6 Battle Round (victory conditions). The split grew because #2/#3 turned out to depend on a unit-command foundation that didn't exist yet (#4), and #6 turned out to depend on a combat/damage layer that also didn't exist yet (#5) — both surfaced mid-session, not upfront.
**Apply when:** Starting a new `/ba` or `/arch` session on MechTS — the full Phase 1 core loop (state machine, economy, espionage, unit command, combat, battle/victory) is now spec'd across issues #1–6, all `phase-1`. Known deliberately-deferred follow-on work, each flagged as its own future issue inside these specs: enemy AI decision-making (economy production choices, espionage targeting, battle combat/surrender behavior), unit roster content (Mechs/Power Armor/etc. beyond Harvester/Saboteur), Campaign structure (mission chaining, hub/mission-select map — though the hub concept itself is confirmed), mission objective authoring (the GDD's Game Types: Defensive/Attack/Escort/Espionage/Support/Reinforce), CameraManager, all UI, tech/upgrade trees, and multiplayer/co-op (explicitly Phase 2, not touched).

### 2026-08-18 — BA — Menu UI split into HUD / Mission End / Main Menu (issues #7–9)
**Context:** Drew dumped a fresh, unordered feature list into `docs/Requirements.md` (per [[design-profile]]'s scratch-file pattern) covering RTS features broadly. Asked which to spec first; Drew picked "Menu UI" over CameraManager, audio, and tech trees.
**Learning:** While scoping "unit management" UI, reading `BuildingPlacement.cs` and `ProductionQueue.cs` (both shipped under issue #2) turned up doc comments explicitly stating their public methods (`SelectBuildingToPlace`, `TryEnqueue`) are "intended to be called by a future build-menu UI" — i.e. the core loop is currently unplayable by clicking anything, since nothing calls them yet. This wasn't mentioned in Requirements.md at all; it only surfaced by reading the already-shipped economy code before drafting the HUD spec. Also split "Menu UI" into three issue-sized specs (HUD #7, Mission End #8, Main Menu #9) rather than one mega-issue, consistent with [[design-profile]]'s confirmed preference — sequenced HUD first since it unblocks manual/Play Mode verification of #1–6, not just because it was asked first.
**Apply when:** Before specing any new UI/interaction system, grep the already-shipped code for doc comments or public methods that read as "intended for a future X" — these are a stronger dependency signal than anything in Requirements.md or the GDD, since they're left by `/dev` sessions that hit the gap directly. Also: when a designer request bundles multiple screens/panels under one label (like "Menu UI"), ask scoping questions per-screen before drafting, then split into separate sequenced issues rather than one spec.

### 2026-08-19 — BA — Camera Manager: keyboard pan collided with an already-shipped unit hotkey
**Context:** Requirements.md just says "Camera manager" with no control-scheme detail; drafting the spec for issue #10, the obvious default for RTS keyboard camera pan is WASD.
**Learning:** `CLAUDE.md`'s already-shipped hotkey reference (`MoveCommand`, issue #4) binds `S` to Stop. WASD pan would make `S` do double duty — pan the camera south AND stop a selected unit's movement in the same keypress. Caught this by re-checking the new spec's control scheme against the existing hotkey reference before drafting, not after; Drew confirmed switching to arrow keys (rather than WASD-with-collision or remapping the existing Stop hotkey) once the conflict was surfaced.
**Apply when:** Specing any new keyboard input system (camera controls, future hotkeys, etc.) — always check proposed keybinds against `CLAUDE.md`'s existing hotkey reference (currently: `Move/Attack: Right-click`, `Stop: S`, `Set Group: Ctrl+0-9`, `Recall Group: 0-9`) before presenting options to the designer, and surface any collision explicitly as its own scoping question rather than silently picking a side.

### 2026-08-19 — BA — Audio: the asset pack already had real SFX matching already-shipped systems, which changed the issue's scope
**Context:** Requirements.md just says "Audio handling abilities" with zero detail — the default assumption going in was a foundation-only issue (AudioManager plumbing, no real content, since no assets were confirmed to exist).
**Learning:** Grepping the asset pack turned up `Assets/TopDownAssets/Common/Audio/SoundFx/` with `MachineGunFire`, `MachineGunReload`, `BulletImpact`, `EngineLoop` — real clips that map directly onto already-shipped systems (`Weapon`, `VehicleAnimationDriver`). Checking how the pack's own `Turret.cs`/`Vehicle.cs` originally used them (`AudioSource.PlayOneShot`, speed-driven volume/pitch) gave a proven reference pattern to spec against instead of guessing an API shape. This flipped the recommended scope from "foundation only, wiring deferred" to "bundle foundation + wiring," since real assets already existed for exactly what's already built — the same "check the pack before assuming a placeholder is needed" discipline `/dev`'s `PATTERNS.md` already documents for sprite art, just not yet applied to audio.
**Apply when:** Specing any "add X" request that sounds like it needs new content (audio, art, VFX) — grep `Assets/TopDownAssets/` for existing real assets *before* assuming a foundation-only/placeholder scope. If real assets already exist for systems that are already built, that's a strong signal to bundle wiring into the same issue rather than defer it. Also: `MachineGunReload.wav` exists with no mechanic to attach it to (no reload/magazine system) — left unused and flagged as an Open Question rather than inventing a mechanic just to consume an asset.

### 2026-08-19 — BA — Minimap surfaced a missing API on Camera Manager (#10), amended before either started dev
**Context:** Speccing Minimap (issue #12) right after Camera Manager (#10) in the same session — click-to-jump-on-minimap needs the main camera to snap to an arbitrary world position, which #10's spec (pan/zoom/bounds/F1-F4 saved locations) didn't cover.
**Learning:** Unlike the earlier "foundational systems surface after the issues that assumed them" case (issue #4 identified after #2/#3 already shipped), this was caught *before* either issue started dev — so the fix was a direct `gh issue edit` amendment to #10 adding `JumpToPosition(Vector3)` to its acceptance criteria, plus a `gh issue comment` explaining why, rather than a new standalone issue or a retroactive-dependency note. Cheaper to catch and fix pre-dev than post-ship.
**Apply when:** A new spec needs one more method/field on an *already-pushed-but-not-yet-dev'd* issue — amend that issue directly (edit + explanatory comment) rather than treating the gap as this issue's own scope or leaving it as an unresolved cross-issue dependency. Only fall back to a separate follow-up issue if the earlier issue has already shipped/closed.

### 2026-08-19 — BA — A full "Universal Sound FX" library (~3,300 files) was missed during the Audio Manager spec because the search only covered one known folder
**Context:** Re-reading `docs/Requirements.md` at the start of this `/ba` session (per the now-standard practice of re-checking it for new content) turned up a new line: "Review sound files for Vehicles and Weapons in Universal Sound FX... include more as we move through." A glob search confirmed `Assets/Universal Sound FX/` exists with ~3,300 categorized, thematically-appropriate files (`WEAPONS/SciFi/Blasters_Simple`, `Plasma_Cannons`, `Shock_Rifle`, full vehicle/tank/spacecraft categories) — none of which were used when issue #11 (Audio Manager) was specced/shipped, because that session's asset search only checked `Assets/TopDownAssets/Common/Audio/` (the folder the pack's own scripts referenced) and never searched the wider `Assets/` tree for other audio content.
**Learning:** The "check the asset pack for real content before assuming a placeholder is needed" discipline (already logged for issue #11's SFX wiring) needs to mean *searching the whole project*, not just the specific pack folder a related script already references. A much better-fitting, already-imported library sat completely undiscovered for an entire issue's lifecycle.
**Apply when:** Specing or reviewing any future content-dependent feature (art, audio, VFX) — glob broadly across `Assets/` for the asset *type* needed (e.g. `**/*.wav`, `**/*Sound*/**`) before concluding what's available, not just the one folder that seems obviously relevant. This is now flagged as its own backlog item ("Audio content pass — Universal Sound FX") for whenever it's prioritized.

### 2026-08-19 — BA — Map Editor (#17, #18): first Editor-tooling spec, and "no terrain art exists yet" reshaped the whole first issue
**Context:** Speccing the Map Editor from Requirements.md's fully-fleshed-out line (Warcraft II-style paint-the-map tool). This is the project's first spec for a developer-facing Editor tool rather than player-facing gameplay — the standard "As a player, I want..." User Story template didn't fit and was adapted to "As a designer, I want...".
**Learning:** (1) Checking Unity's actual built-in capabilities (`Window > 2D > Tile Palette` already exists) before designing a custom terrain-painting tool avoided speccing redundant work — split into #17 (adopt Unity's stock Tilemap/Tile Palette, near-zero custom code) and #18 (a genuinely custom prefab-painting tool, since Unity has no built-in equivalent for that). (2) A `Glob` check for terrain/ground texture art across the whole imported asset base (not just the one folder already known) turned up nothing — the current `Ground` is a flat solid-color quad, no texture at all. This materially changed #17's scope: shipped as infrastructure-only with one placeholder tile, explicitly not blocked on art that doesn't exist, rather than a fuller terrain-painting spec. (3) A quick check for an existing `ResourceNode` prefab (none exists — today's scene nodes are hand-configured instances, not prefab-backed) folded "create real Ore/Biomass/Gold node prefabs" into #18's own scope rather than leaving it as an unstated dependency.
**Apply when:** (a) Specing any Editor/tooling feature (not player-facing) — adapt the User Story template's framing ("As a designer...") rather than forcing a player-facing phrasing that doesn't fit. (b) Before speccing any content-painting/authoring tool — check what Unity's stock Editor already provides (Tile Palette, Prefab Painter-equivalents) before assuming custom code is needed; the real work is often narrower than the initial ask implies. (c) Same broad-glob discipline as the Universal Sound FX entry above — check whether the actual art/prefab assets a spec assumes exist really do, project-wide, before finalizing scope.

### 2026-08-20/21 — BA — Enemy Unit/Building Inspection (#24): "let players click enemies to see info" required inventing parallel state, not extending existing selection
**Context:** Requirements.md just says "Ability to select enemy units and buildings to see information." The obvious-looking implementation would extend `SelectionController.SelectSingleAt`'s existing `Faction.Player` filter to also accept enemy hits, reusing `UnitManager.SetSelection`/`SelectedBuilding` as-is.
**Learning:** That would have been a real, dangerous bug. `UnitManager.MoveSelectedTo`/`StopSelected` (read by `AttackCommand`'s right-click resolution) have zero faction checks anywhere — they act on whatever's in `SelectedUnits`, full stop. If an enemy unit ever entered that list, right-clicking would issue it a real move order — the player could puppet enemy units by clicking them. The correct design keeps enemy inspection completely parallel: new `SelectedEnemyUnit`/`SelectedEnemyBuilding`/`SelectedEnemyMainBuilding` properties on `SelectionController`, never touching `UnitManager` at all, so "no command capability" is structurally guaranteed (no order-issuing code path reads the new fields) rather than enforced by a permission check someone has to remember to add. This also meant `AttackCommand` needed zero changes — right-click already no-ops harmlessly when `SelectedUnits` is empty, which is exactly the state during enemy inspection.
**Apply when:** Any future spec that "lets the player select/target something not normally selectable" — check whether the existing selection state is read by any command-issuing code with no ownership/faction check, before assuming the new case can reuse that state. If commands are issued off a shared list with no per-item ownership check, a new category of selectable thing needs its own separate state, not an extension of the filter.

### 2026-08-21 — BA — A shipped, arch-approved decision (#20, Main Building Invulnerability) got fully reversed one session later, after the designer actually saw it in play
**Context:** `docs/Requirements.md` line 28 originally read "Unable to attack main building... bullets simply pass through" — specced, arch-reviewed, and shipped as issue #20 the same session. The very next `/ba` session, a new Requirements.md line said the opposite: "The main building doesn't have health... We need to add health to this building and make it attackable," with new core-loop-relevant detail (the MCB's destruction should factor into the wipeout victory condition) that wasn't part of the original ask at all.
**Learning:** This wasn't a misunderstanding or a stale requirement — Drew changed his mind after actually seeing the invulnerable main building in a real playthrough and realized it should be a real, attackable structure whose loss matters for victory. The correction came with genuinely new design detail (the wipeout-condition tie-in) that only surfaced once he'd thought about it in the context of actual play, not on paper.
**Apply when:** (a) Never treat a shipped/closed issue's decision as permanently settled just because it's closed — always re-read the *current* `docs/Requirements.md` in full at the start of every `/ba` session, even for topics that already have a closed issue; a reversal can arrive as an update to the same line that originally requested the now-reversed behavior. (b) When a reversal touches a shipped issue's whole premise (not just a field/detail), spec it as a new issue that explicitly supersedes the old one (note the old issue number, flag that its `CLAUDE.md`/completion-comment claims are now stale) rather than trying to "amend" a closed issue after the fact. (c) A design reversal is often accompanied by new information the original ask didn't have (here: how MCB destruction interacts with victory conditions) — dig for that context rather than treating the reversal as a simple on/off flip.

### 2026-08-20 — BA — HUD complaints (#19) mapped to two already-shipped bugs, not new layout work
**Context:** `Requirements.md`'s HUD cleanup lines (overlapping top-left canvases, "Selection info floating next to" the control groups) read as layout/relocation requests. Reading the actual shipped code first, then a designer-provided screenshot, changed the diagnosis entirely.
**Learning:** (1) The "2 overlapping canvases showing Player(blue)/Enemy(red)" complaint was `Utilities/DebugHud.cs` — already documented in `CLAUDE.md` as non-shipping scaffolding, but still hand-placed and active in `Assets/Scenes/SampleScene.unity`, drawing over the real (already player-only) `ResourcePanel`. A component being flagged "not meant to ship" in `CLAUDE.md` doesn't mean it's actually inert — it can still be a live GameObject in the committed scene file; grep the `.unity` scene file directly, don't just trust the doc comment. (2) The "Selection info floating next to control groups" complaint, once a screenshot was shared, turned out to be a real coordinate-math bug: `UIFactory.CreateRect` sets `pivot = anchor`, so for any BottomRight/TopRight-pivoted element, `anchoredPosition.x` places that element's RIGHT edge, not its left. `SelectionPanel.Awake()`'s child offsets (`_selectionText`, `_groupIndicators`, `_detailCard`) were authored assuming left-edge semantics, so they rendered entirely outside/left of their own background panel. `BuildMenuPanel`/`ResourcePanel` happened to author their offsets in the semantics that actually match `CreateRect`'s real behavior, so this bug was isolated to `SelectionPanel` alone.
**Apply when:** (a) A `/ba` UI complaint sounds like a layout/relocation ask — read the actual panel code (and the scene file, for anything that might be hand-placed rather than script-instantiated) before assuming new layout work is needed; it may already be a bug with a precise, findable root cause. (b) Any future spec touching `UIFactory.CreateRect`-based positioning for a BottomRight/TopRight-anchored element — remember `anchoredPosition.x` measures from that element's own right edge, not left, and check existing sibling offsets in the same file for the same left-edge-assumption mistake before trusting them as a positioning reference.

### 2026-08-22 — BA — Zoom-Aware Positional SFX (#33): the orthographic camera doesn't move, so vanilla 3D audio silently wouldn't respond to zoom at all
**Context:** Drew described wanting Harvester sound to originate positionally and get quieter/louder with camera zoom — flagged as genuine implementation uncertainty ("not sure if this is possible"), the same signal pattern as the earlier Map Editor spec (see [[design-profile]]).
**Learning:** Reading `AudioManager.cs` and `CameraManager.cs` before answering surfaced two things a surface-level "yes, use 3D audio" answer would have missed: (1) `VehicleAnimationDriver`'s engine-loop `AudioSource` has no `spatialBlend` set at all (defaults to 0, fully flat 2D) despite reading like it should already be positional — pooled one-shot SFX (`Weapon`/`BulletEffect`) already are (`spatialBlend = 1`), so the two systems were inconsistent. (2) `CameraManager.ApplyZoom` only changes `orthographicSize`, never the camera's actual `transform.position` — so even correctly-configured native 3D distance falloff would never respond to zoom, since the listener's real distance to any source never changes. The fix that reuses Unity's engine instead of hand-rolling volume math: dolly the camera's height in lockstep with orthographic size (invisible in ortho rendering, but makes native distance falloff respond to zoom "for free"). Presented as a recommended option via AskUserQuestion against a hand-rolled-math alternative; picked immediately.
**Apply when:** Any future spec touching audio-vs-camera interaction in this project — remember `CameraManager` never moves the camera's position for zoom, only `orthographicSize`, so any feature assuming "zoom = camera distance changes" needs this dolly (or equivalent) explicitly designed in, not assumed to already work. More generally: when a designer flags "not sure if this is possible," grep the actual consuming code for existing-but-inconsistent wiring (one system already doing the thing, a sibling system silently not) before proposing a build-from-scratch answer.

### 2026-08-22 — BA — Terrain Elevation (#35): "SC2-style height" is three separable mechanics, and one has a hard missing prerequisite
**Context:** Drew asked for a "layer system to simulate height," referencing SC2 without describing the mechanic in detail — same "not sure how it's done, something like that" signal as the earlier Map Editor request (see [[design-profile]]).
**Learning:** Before drafting anything, grepped for an existing fog-of-war/vision system (`FogOfWar`, `VisionRadius`, `LineOfSight`) and found none at all — SC2's height mechanic is actually three separable pieces (visual tiering, pathing-blocking via ramps, vision advantage for high ground), and the vision piece has a hard, unbuilt prerequisite (no FoW system exists in this project). Also checked the actual NavMesh bake settings via `unity-mcp` (`NavMesh.GetSettingsByID(0)`: Max Slope 45°, Step Height 0.75) before writing acceptance criteria — this turned a vague "make ramps work" requirement into a precise, testable one (platform height must exceed 0.75 to actually block, ramp slope must stay under 45° to auto-bake as walkable), and confirmed the mechanic needs zero NavMesh Area/OffMeshLink authoring, just correctly-dimensioned geometry. Presented the three-way scope split via `AskUserQuestion` with a recommended middle option (pathing-blocking only, vision deferred) rather than either building the vision system unprompted or silently scoping it out; picked immediately, matching the pattern of accepting a well-reasoned researched recommendation.
**Apply when:** (a) A designer references a specific real-game mechanic ("like SC2", "like Warcraft II") without spec'ing the exact behavior — decompose it into its actual separable sub-mechanics before drafting, since a big genre-mechanic name usually bundles 2-3 independently-scopable systems, and check whether any of them have a hard unbuilt prerequisite (here: fog-of-war) before assuming the whole thing is one issue. (b) Before writing acceptance criteria for anything touching NavMesh/pathing in this project, query the actual live bake settings (`NavMesh.GetSettingsByID`) rather than assuming defaults — turns vague behavioral claims into concrete, checkable numbers.

### 2026-08-22 — BA — Fog of War (#36/#37): a deferred sub-mechanic from the previous session's spec turned out to have its data model already sitting unused in the codebase
**Context:** Speccing Fog of War, the very system the Terrain Elevation spec ([[requirements-vs-spec]]'s same-day entry) had just deferred a "vision advantage" half of. Grepped for any existing detection/vision code before assuming a from-scratch data model.
**Learning:** `BuildingDefinition.isDetectionCapable`/`detectionRadius` already exist, fully unused (zero code reads them, confirmed via grep) — and critically, the Inspector header above them literally reads `[Header("Detection (Espionage counter)")]`. This is a strong, concrete signal of original design intent (detection buildings exist to counter the Saboteur/Espionage mechanic, issue #3) that would have been easy to miss and reinvent as a brand-new field. Reused it directly: detection-capable buildings get `detectionRadius` as their vision radius instead of the new baseline `visionRadius` field every other building gets. Also: Drew picked the higher-scope "3-state" fog persistence option over the recommended simpler 2-state one — third confirmed instance of this pattern (see [[design-profile]]'s Unit Orders/Rally Points note) — and the resulting spec had to design real new data-model complexity (a "remembered static building marker" concept) that the recommended 2-state option would have avoided entirely.
**Apply when:** (a) Before speccing any system that sounds new, grep for dormant/unused fields on existing config `ScriptableObject`s first (especially ones with a suggestive `[Header]` or field name) — this project has a real pattern of fields being added ahead of the system that would consume them (also true of `PassiveGeneration` on `UpgradeStatType`, per an earlier `/arch` entry), and reusing them is both cheaper and honors original intent better than inventing a parallel field. (b) Continue defaulting to presenting the higher-scope option as available (not hidden) even when recommending the simpler one — Drew has now picked the non-recommended, higher-scope option three separate times across three different features.

### 2026-08-23 — BA — Requirements.md restructured into Implemented/Needs-Your-Call/Open, and a "reported bug" line turned out to describe a feature that was never wired up at all
**Context:** Drew asked for a full review of `docs/Requirements.md` against shipped state, then asked to permanently restructure the file: compact anything implemented down to its GitHub issue number instead of leaving the full requirement text sitting alongside already-done work, so the file stays legible as a live backlog rather than an ever-growing dump.
**Learning:** (1) Rewrote the file into three sections — **Implemented** (one line per item, issue number only), **Needs Your Call** (a shipped decision that reversed or contradicts the original ask — currently just #28's main-building-attackable reversal of #20), and **Open** (unimplemented, ready for `/ba` to pick up next). ### 2026-09-03 — BA — "Units appear floating" (issue #85) — a bug report disguised as a visual-review ask, root-caused before writing anything
