# Patterns

### 2026-08-29 — Dev — Issue #68 (correcting #66 again): a flat plate's UV range reveals whether to rotate the mesh or scroll its texture, and a "looks identical" side-by-side capture doesn't disprove continuous motion
**Context:** #66's track animation shipped as `Transform.Rotate` on the tracks object, only sanity-checked at a single static test angle during dev. The designer's first real gameplay session showed it visibly "just spinning" rather than rolling.
**Learning:** (1) Read the actual mesh's UVs (`Mesh.uv`) rather than guessing at the right technique — the tracks mesh's U range tiled far past `0-1` (roughly `[-6.6, 7.8]`) while V stayed tight in `0-1`, the textbook signature of a texture meant to be UV-scrolled to fake rolling motion on a flat plate, not literal geometry rotation (which reads as tumbling for a flat shape — exactly the "just spinning" symptom). (2) After switching to a `MaterialPropertyBlock` UV-offset scroll, two static side-by-side captures at different offset values looked visually identical to the eye — before concluding the fix didn't work, verified with direct pixel sampling at the same world point at each offset and found a real, measurable color difference, confirming the mechanism genuinely works. Continuous per-frame scrolling reads as real motion over time even when two isolated frames look nearly the same compared side by side — the same reason a spinning wheel photographed at two random instants doesn't obviously prove motion either. Trusting the "looks the same" visual impression here would have led to a wrong conclusion.
**Apply when:** (a) For any future flat "wheel"/"tread"/"conveyor" mesh from an asset pack, check `Mesh.uv`'s actual range before choosing rotation vs. texture-scroll — a range that tiles far past `0-1` on one axis while staying tight on the other means the artist intended texture-scrolling. (b) When verifying a continuous-motion effect (scrolling, gradual color change, slow animation) via static captures, don't trust "the two screenshots look the same" as proof it's broken — sample actual pixel values at the same point under both conditions before concluding a subtle continuous effect isn't working; direct pixel proof is stronger evidence than eyeballing a side-by-side comparison for effects that are inherently subtle per-frame but cumulative over time.

### 2026-08-29 — Dev — Issue #67 (correcting #66): a hand-rolled claw animation was fighting a real, better-quality one the model already shipped with — should have checked before writing any code
**Context:** #66 shipped a sine-wave rotation script for the Harvester's claws, assuming the 3D model had no built-in animation for them (reasonable-looking assumption — the pack's `AnimatorController` has zero parameters, nothing to obviously drive it). The designer caught this by directly inspecting the imported asset in the Editor and pointed out the model's `Art` child already has a real `Animator` assigned.
**Learning:** Inspected the actual `AnimatorController` and its one `AnimationClip` via `AnimationUtility.GetCurveBindings` (not assumed from the controller having no parameters) — confirmed a real, artist-authored 1.5s looping clip with full quaternion keyframes on both claw transforms already existed, and was the controller's *default* state, meaning it was already playing (constantly, unconditionally) from the moment the object spawned, colliding with the hand-rolled script's own `Update()`-time rotation of the identical transforms every frame. The zero-parameters detail that looked like "nothing here to use" actually meant "the controller can't gate itself" — a different problem (needs external gating) than "there's nothing to gate" (needs a script to fake it). Fixed by keeping the model's own animation and toggling `Animator.enabled` externally instead of touching the claw transforms directly at all.
**Apply when:** Before writing ANY hand-rolled animation/rotation script for a part of an imported 3D model — first check whether that model already ships a real `Animator` with actual clips, via `AnimationUtility.GetCurveBindings` on whatever clips its `AnimatorController` references, not just by checking whether the controller has parameters (a controller with no parameters can still have a real, currently-always-playing clip — the two facts are independent). This applies to every future 3D asset-pack conversion in this project, not just the Harvester — check first, build second.

### 2026-08-29 — Dev — Issue #66 (Harvester Track/Claw Rotation): a private `MonoBehaviour` field with no `[SerializeField]` is invisible to `SerializedObject`, and reflection fails even for a trivial zero-distance NavMesh path
**Context:** Needed to force `HarvesterGatherBehavior`'s private `_state` field to `Gathering` for a live verification of the new claw-oscillation animation, without adding a test-only public setter to shipped code.
**Learning:** (1) `SerializedObject.FindProperty("_state")` returned null — Unity's default serialization only picks up private fields explicitly marked `[SerializeField]`; a plain private field (even of an otherwise-serializable nested enum type) is genuinely invisible to `SerializedObject`, not a tooling limitation. (2) `System.Reflection.FieldInfo.SetValue` on the same field then threw `NullReferenceException` — confirming this project's already-documented reflection-unreliable-in-`RunCommand` finding extends to `FieldInfo`, not just the previously-documented `MethodInfo.Invoke`/`Type.GetMethod`. (3) Tried the "legitimate" path instead — call the real public `AssignToNode` API with the harvester teleported directly onto the node (zero-distance path) to sidestep needing multiple simulation frames. Even this failed: `Agent.pathPending` stayed `true` and `Agent.remainingDistance` stayed `Infinity` after 5 forced `Update()` ticks — confirming the frozen-player-loop limitation isn't about long/complex paths specifically, `NavMeshAgent`'s internal path resolution needs *some* real simulation tick to run at all, and this environment cannot force even one.
**Apply when:** (a) Never assume a private `MonoBehaviour` field is reachable via `SerializedObject` — check whether it has `[SerializeField]` first (or just grep the class); if not, don't bother trying, and don't fall back to reflection either (per this entry, both are unreliable here). (b) If a future verification needs to force a state that ultimately depends on `NavMeshAgent.pathPending` resolving, don't try to minimize the path distance to work around the frozen-loop limitation — it doesn't help, the tick itself is the blocker. Verify what's directly reachable (component wiring, the gating logic's *false*-state behavior, the underlying formula in isolation) and say plainly what couldn't be forced, matching the precedent already set for #33/#47's verification gaps.

### 2026-08-29 — Dev — Issue #65 (3D Roster Conversion): a real Directional Light alone was enough — #64's Volume-disable finding didn't generalize, and re-verifying was cheaper than assuming
**Context:** #64's exploratory findings said the scene needed *both* the Global Volume disabled and light intensity boosted to make lit 3D content visible — the natural reading was "the Volume Profile needs a real tuning pass before any of this looks right," which #65's arch review folded into required scope.
**Learning:** Added one real `Directional Light` (intensity 1.5, not #64's under-tuned 1.2) and left the Volume Profile completely untouched — it worked. Inspecting the actual Volume components first (`Tonemapping` Neutral, `Bloom` 0.25, `Vignette` 0.2) showed nothing extreme enough to explain #64's grey-wash result on its own; the real cause was almost certainly just the too-low light intensity, and disabling the Volume in #64 was likely masking that rather than being independently necessary. Saved a real chunk of this issue's effort.

### 2026-08-29 — Dev — Issue #65: fixing a dangling `[SerializeField]` child-reference must happen *before* destroying the old `Art` child, not after
**Context:** `HarvesterUnit.prefab`'s `VehicleAnimationDriver._tracks` was wired directly to two `WheelAnimation` components inside the sprite `Art` child being replaced (flagged during #65's `/arch` review as the same dangling-reference bug shape already documented for the Enemy-variant art swap).
**Learning:** Cleared `_tracks` via `SerializedObject.FindProperty("_tracks").ClearArray()` **before** calling `Object.DestroyImmediate` on the old `Art` GameObject, not after. Order matters here for a subtle reason: once the referenced `WheelAnimation` objects are destroyed, `SerializedObject`'s own array-shrinking/reference-clearing can behave inconsistently against already-dangling entries in some Unity versions — clearing the array while the references are still valid objects (just about to be destroyed) is unambiguous and doesn't depend on Unity's null-vs-missing-reference serialization quirks. `VehicleAnimationDriver.cs` itself needed zero code changes — its `Update()` loop over `_tracks` is already a safe no-op on an empty list, and `SetEngineSound`/the engine-audio hookup lives entirely outside the `_tracks`-dependent code path.
**Apply when:** Any future prefab conversion has a sibling component with a direct `[SerializeField]` reference into the `Art` child being replaced — clear/null that reference explicitly (via `SerializedObject`, not direct field access on a loaded prefab's component) *before* destroying the old `Art` child, not after, and verify with a real forced multi-tick `Update()` call (`SendMessage` loop) on a live spawned instance afterward, not just a single frame or a code read.

### 2026-08-29 — Dev — Issue #65: measuring a nested Art child's real `Renderer.bounds` is the reliable way to size a building's collider to a 3D model, reusable for every future building conversion
**Context:** `MainBuilding`/`EconomicBuilding` had no prior `Art`-vs-collider separation at all (single flat placeholder-cube GameObject) — converting them needed a real, non-guessed way to size the new `BoxCollider` to whatever 3D model got nested in.
**Learning:** After instantiating the model as the `Art` child, collected every `Renderer` in its hierarchy via `GetComponentsInChildren<Renderer>()`, unioned their `.bounds` (`Bounds.Encapsulate`), then converted that world-space bounds into the root's local space (`Transform.InverseTransformPoint` for center, divide by `lossyScale` for size) to set `BoxCollider.center`/`.size` directly. This is a general, reusable technique — worked identically for `CommandTowerBlue` (`6.55×9.52×8.33`) and `ResourceExtractorBlue` (`2.12×2.22×0.98`) despite wildly different model complexity/hierarchy depth, with zero manual measurement or guessing.
**Apply when:** Any future issue converts another 2D building prefab (Barracks, Drone Factory, Technology Plant, Robotics Plant, turrets, etc.) to a 3D model from this or any future pack — reuse this exact measure-then-set pattern rather than eyeballing collider dimensions, and reuse the root-scale-reset-to-uniform check from the same issue (any placeholder-cube-era building prefab is a candidate for the non-uniform-scale bug per the #45/#65 precedent).

### 2026-08-28 — Dev — Issue #63, third fix (the real one): a whole art pack was silently incompatible with vertical-axis rotation, and isolating one instance at native scale proved it definitively
**Context:** After two correct spacing fixes (drag-repaint stacking, then single-batch minimum spacing), the designer's next screenshot still showed "wrong" trees — but this time correctly spread apart, with the designer specifically calling out "rotation and flipping" rather than overlap. Worth taking that description at face value instead of re-checking spacing a third time.
**Learning:** Isolated one specific rotated real instance (SpriteRenderer-toggle technique, same as the first #62 diagnosis) and framed the camera close on it alone — at ~90° Y rotation, the tree was genuinely broken: trunk sheared to one side, canopy bunched to the other, nothing like a tree "facing a different direction." A side-by-side Rock comparison at 0° vs. 90° confirmed the identical breakage. This proved the art itself, not the code, was the problem: `RPGW_GL_v2.0`'s sprites are drawn in a fixed-perspective "2.5D" style (an implied single camera angle baked into the pixels, image-Y representing height/depth — the common RPG-Maker tile convention) rather than true orthographic top-down like every previously-used pack (`TopDownAssets`, confirmed genuinely bird's-eye per `CLAUDE.md`). Spinning such a sprite around the world-vertical axis doesn't rotate the depicted object — it shears the flat picture, since only one viewing angle was ever painted. Fixed by disabling `randomizeRotation` entirely on both affected brushes and resetting rotation to identity on every already-painted real instance in the scene (not just future paints) — a design-time art-pack constraint, not something any amount of spacing/rejection-sampling code could have fixed.
**Apply when:** (a) A designer's bug description uses a specific word ("rotation," "flipping") — investigate that specific claim directly (isolate one instance, compare rotated vs. unrotated at native scale) rather than assuming a previously-diagnosed cause (spacing, overlap) is still the culprit just because it produces a superficially similar "looks wrong" symptom. This issue had three genuinely independent causes behind the same rough visual complaint. (b) Before enabling `randomizeRotation` on any future brush sourced from a new art pack — don't assume it's safe by precedent from `TopDownAssets`; verify the pack's actual drawing convention (true top-down vs. fixed-perspective/isometric tile art) first, e.g. by rendering one instance at 0° and 90° side-by-side exactly as done here, since a perspective-style pack will always break under rotation regardless of how it's tuned. (c) When a code-side fix corrects previously-painted content going forward but existing painted instances are already visibly broken, fix the real objects directly (not just the brush asset) rather than leaving the designer to manually notice and repaint — here, resetting rotation on the 4 already-placed trees was as important as the brush setting change.

### 2026-08-28 — Dev — Issue #63, second fix: a single splash batch's own random points need minimum-spacing enforcement too, not just the drag-repaint gate
**Context:** Immediately after the drag-spacing fix (previous entry), the designer's next screenshot showed the identical "chained trees" symptom from a *single* click — confirmed via ground-truth position dump this was genuinely one batch (4 trees, all within the expected radius), not multiple stacked batches.
**Learning:** `PaintSplash` picks each of `splashCount` positions via `Random.insideUnitCircle * splashRadius` completely independently, with no minimum-distance constraint between them. With only 4 samples, real variance means 2-3 candidates land close enough to touch/overlap a non-trivial fraction of the time, regardless of how generously the overall radius is tuned — this is a fundamentally different failure mode from both prior fixes (per-batch density, and drag-repaint stacking), the third independent cause of the same visual symptom. Fixed with rejection sampling: each candidate is checked against every already-placed offset in the same batch, retried up to `MaxSpacingAttempts=20` times if too close, minimum gap set to `splashRadius * SplashSpacingFraction(0.5)` — proportional to the brush's own radius rather than a flat distance, so it scales down correctly for small-object brushes (`Plant1/2/3Cluster`, radius 3) instead of forcing them unnaturally sparse. Verified quantitatively (30 simulated batches, worst-case pairwise distance 4.01 against a 4.0 target — the rejection sampling reliably holds) before doing a live repaint+capture, rather than trusting a single visual sample the way the earlier two fixes initially were (each of which turned out to have another layer underneath).
**Apply when:** (a) A "same visual symptom, different cause" report keeps recurring on splash-brush content after a fix — don't assume the latest fix was insufficient; ground-truth-check the *specific* new report first (position dump, batch count) to identify which of potentially several independent causes is actually still active. This issue alone had three: per-batch density (asset tuning), drag-repaint stacking (multiple batches), and single-batch spacing (this entry) — all producing the identical-looking "chained canopy" symptom. (b) Any future rejection-sampling/retry loop introduced into `MapEditorWindow` — verify it quantitatively via simulation across many trials before trusting one visual capture; a single lucky/unlucky random draw doesn't prove a probabilistic fix actually holds.

### 2026-08-28 — Dev — Issue #63 (splash-brush drag spacing): a second real bug hid directly underneath the first one's fix, and the designer's continued real-world use caught it within minutes
**Context:** Immediately after retuning `Brush_TreeGreenCluster`/`Brush_RockCluster` to a looser per-batch density (the previous same-day entry), the designer reported the splash brush was *still* "placing trees strangely" compared to the single-tree brush — with a screenshot showing far more trees in one clump than any single splash batch (`splashCount=4`) could produce.
**Learning:** Dumping every real `Prop_Tree_Green` instance's position and clustering them confirmed 15 trees existed where at most 4-8 (one or two clean batches) were expected. The actual cause was one level deeper than the density tuning: `MapEditorWindow.TryPaint`'s drag-repaint spacing gate (`MinPaintSpacing = 1.5f`) is a flat constant shared by every brush type — correct for an ordinary brush (paint a dense line by dragging every ~1.5 units) but wrong for a splash brush, whose *single click* already scatters instances across a much larger `splashRadius` (8, post-fix). Dragging at the same 1.5-unit cadence fires an entirely new full batch almost on top of the last one on every drag step, unioning consecutive batches into one dense mass regardless of how loosely any single batch is tuned — the exact same *visual symptom* as the first bug (chained/overlapping canopies), but from a structurally different cause (multiple batches, not one dense batch). Fixed with `Mathf.Max(MinPaintSpacing, _selectedBrush.splashRadius)` as the gate specifically when `isSplashBrush` is true. Verified by mirroring `TryPaint`'s exact gating logic in a `RunCommand` script against a simulated 24-unit drag at realistic ~1.8-unit step resolution: 13+ batches before the fix, 3 well-spaced batches after, each origin confirmed `>= splashRadius` apart.
**Apply when:** (a) A "looks wrong" report on a splash-painted cluster persists even after confirming a specific brush's density/tuning is correct — check the *drag/repaint* path next, not just the single-batch math; two independent causes can produce the identical visual symptom (chained overlapping canopies), and fixing one doesn't rule out the other. (b) Any future spec/fix touching `MapEditorWindow`'s paint-spacing logic — remember `MinPaintSpacing` is currently a single flat constant assumed correct for every brush; a brush type whose single paint action has its own spatial footprint (splash radius today, potentially something else later) needs the repaint gate scaled to that footprint, not the ordinary-brush constant. (c) This fix is shared tool code, so it silently corrected the identical latent bug in every pre-existing splash brush (`Brush_TreeCluster`, `Plant1Cluster/2/3Cluster`) with zero data changes — when a Map Editor tool-code fix has this shape (a shared code path underlying multiple brush assets), check whether it's fixing more than the one brush that surfaced it, and say so explicitly rather than scoping the fix as brush-specific.

### 2026-08-28 — Dev — Issue #62 follow-up: a designer-reported "rotation problem" on real painted content was actually splash-cluster overlap density, isolated by toggling one SpriteRenderer at a time
**Context:** After #62 shipped, the designer painted a real `Brush_TreeGreenCluster` in their own Editor session and reported the trees looked rotated wrong — a jagged, connected, snake-like shape instead of distinct trees.
**Learning:** Rather than trusting either the designer's diagnosis or my own prior assumption ("dense overlap matches `Brush_TreeCluster`'s precedent, therefore fine" — logged in this same file, and wrong to leave unquestioned once someone actually looked closely), inspected the *real* user-painted GameObjects directly: dumped every instance's root/`Art` world rotation (confirmed exactly `(90°, randomY, 0°)` on all 6 — mathematically flat, just spun around the vertical axis, no way to misread as tilted) and sorting layer/order (all identical, ruling out a transparent-sort bug). Then, critically, **disabled every sibling `SpriteRenderer` but one** (non-destructive — a component-level toggle, not `DestroyImmediate`, so the designer's real content was trivially restorable) and captured that single isolated instance: a completely normal, correctly-flat tree. This proved the data/rotation was never wrong — the "broken" look was 6 full-size trees' irregular multi-lobed canopy silhouettes (visibly non-convex even in isolation) chaining together into one connected blob the moment `PaintSplash`'s uninforced random scatter placed two of them close together, which only becomes likely at high density (`Brush_TreeCluster`'s inherited `radius=4`/`count=6` was ~74% area coverage for a ~2.8-unit-wide tree). Fixed by loosening `Brush_RockCluster`/`Brush_TreeGreenCluster` to `radius=8`/`count=4`, verified by repeatedly repainting fresh test clusters and capturing until instances read as a clean, separated grove.
**Apply when:** (a) A designer reports something "looks rotated/wrong" on a splash-scattered prop cluster in this project — before assuming a transform bug, isolate one instance at a time via `SpriteRenderer.enabled` toggling (reversible, doesn't touch their real painted content) and capture it alone; a chaining/overlap illusion from a non-convex sprite silhouette is a real, easy-to-misdiagnose-as-rotation failure mode distinct from an actual transform bug. (b) Don't treat "this matches an existing brush's tuning" as proof a density is fine (see this file's earlier, now-partially-superseded 2026-08-28 entry on the same issue) — that only proves consistency with precedent, not that the precedent itself looked right under real inspection; a prop's own art (round vs. lobed/organic silhouette) changes how much overlap actually reads as acceptable at the same radius/count numbers. (c) `Brush_TreeCluster` (pre-#62) was NOT retuned and likely has the identical issue — worth fixing whenever it's next touched, flagged rather than silently carried forward.

### 2026-08-28 — Dev — Issue #62 (RPGW Decorative Props): a flood-fill alpha scan is a reliable, script-only way to slice an unsliced sprite sheet without the Sprite Editor UI or hand-guessed pixel rects
**Context:** `decorative.png` needed 3 specific shapes (a rock, a tree, a bush) sliced out for new prop prefabs. The pack's objects are irregularly sized/spaced on a transparent background — not a uniform grid — so a fixed-cell-size grid slice wouldn't line up, and there's no scripting API for the Sprite Editor's own "Automatic" (alpha-based) slice.
**Learning:** Wrote a `RunCommand` script that temporarily flips `TextureImporter.isReadable`, reads `Texture2D.GetPixels32()`, and flood-fills (8-directional, to bridge anti-aliased 1px gaps) every connected region of alpha>10 pixels into a bounding-box list, filtering blobs under ~150px as noise. This produced a clean, correctly-ordered list of every distinct object on the sheet with exact pixel rects — verified by cropping and rendering each chosen rect back out as a small PNG and viewing it before committing to the slice, rather than trusting the computed rect blind. Once the 3 target rects were confirmed correct, set them directly via `TextureImporter.spritesheet` (a `SpriteMetaData[]`) — still functional via scripting even though the Sprite Editor UI is the normal way to do this.
**Apply when:** Any future spec needs specific shapes sliced out of an unsliced, irregularly-packed sprite sheet (this project has at least 3 more unsliced RPGW sheets — `MainLev2.0.png`, `MainLev_autotiling.png`, `decorative_nograss.png` — deferred from #62 but real candidates later) — reuse this flood-fill-plus-crop-preview technique instead of hand-guessing pixel coordinates from a visual read of the sheet, and always render the chosen rect back out for a visual check before finalizing it.

### 2026-08-27 — Dev — Issue #54 (Battle-Round Tech Swapping): a synthetic, in-memory test upgrade is the safe way to verify tech-tree logic without risking mutating real shipped `.asset` data

### 2026-08-22 — Dev — Issue #35 (Terrain Elevation): a procedurally-built mesh's triangle winding must be verified against actual geometric behavior, never trusted from `SetNormals()` alone — it broke rendering AND NavMesh baking identically, with zero errors anywhere
**Context:** `Platform_Tier1`/`Ramp`'s custom box mesh (base-anchored, so it could scale from an edge instead of its center) rendered as completely invisible and produced zero walkable NavMesh geometry, on every face, in every configuration tried. Both consumers that matter — backface-culling rendering AND Recast's NavMesh voxelization walkability test — read the *actual winding* (cross product of the triangle's own edges), not the stored normal, so a winding bug silently breaks both simultaneously with no distinguishing symptom beyond "nothing renders and nothing bakes here." (2) Separately, both mesh assets also had a null `MeshFilter.sharedMesh` at the *prefab-asset* level — built in memory during original construction but never persisted via `AssetDatabase.CreateAsset` before `PrefabUtility.SaveAsPrefabAsset`, so the reference silently dropped on save with no error at save or load time. **Apply when:** (a) Any future procedurally-built `Mesh` in this project (custom shapes, not `PrimitiveType`) — verify its actual winding behaves correctly by testing render + NavMesh-bake behavior directly (or by comparing against a known-correct built-in primitive of the same intended shape/normals), never assume `SetNormals()` alone makes a face "face" the direction you told it to. ### 2026-09-03 — Dev — Issue #84 follow-up: Unity's Terrain paint tools actually do require a live TerrainCollider, contradicting an assumption stated during the original implementation
**Context:** The designer hit a real block trying to use Paint Trees/Details on `OutdoorTerrain` (deliberately built with no collider per `/arch`'s review) — the Terrain Inspector itself displayed "Painting on this Terrain is not supported without the TerrainCollider component."

**Apply when:** (a) Any future spec/review that wants a GameObject to be "visible but non-interactive" (a collider-free decorative object) and that object needs to be edited via one of Unity's own built-in Editor tools (Terrain painting, Sprite Shape, Tilemap, etc.) — check whether that specific Editor tool actually requires a collider/component to function before assuming "no collider" is achievable; some genuinely do, and that's a legitimate reason to add one back on a dedicated safe layer, not a design compromise to avoid.
