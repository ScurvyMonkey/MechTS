### 2026-08-17 — Arch — Recommended implementation order for issues #1–6
**Context:** Backlog review of the full Economy/Battle Round core loop (issues #1–6). Issue numbering reflects the order they were spec'd in `/ba`, not their dependency order.
**Learning:** Issues #2 (Harvester) and #3 (Saboteur) both narrate their units as extending a `UnitBase` that isn't actually defined until #4; #3's detection-building defense is explicitly built ad hoc against `Turret`/`Projectile` with a stated plan to reconcile it onto #5's `Weapon` component later. Building in issue-number order guarantees rework the specs themselves predict. Recommended order: **#1 → #4 → #2 → #5 → #3 → #6.**
**Apply when:** Advising on or reviewing implementation sequencing for this backlog, or spec'ing new issues that extend `UnitBase`/`Weapon` — check whether the foundation those extensions assume actually exists yet before treating issue number as build order.

### 2026-08-17 — Arch — Elimination conditions must require true elimination, not a momentary zero
**Context:** Issue #6 (Battle Round victory conditions) originally evaluated "no more units," "no more buildings," and "no more economy" as three independent OR-triggered loss conditions.
**Learning:** Because issue #6 also introduced production carryover (unit production continues into Battle Round funded by leftover Economy Round resources), a faction can legitimately enter Battle Round with buildings and resources intact but zero *current* units (e.g. harvesters lost to sabotage, no combat unit built yet). Evaluating "unit count == 0" independently would instant-lose that faction before its carried-over production ever gets a chance to produce anything — defeating the point of the carryover mechanic. Flagged as a required fix before `/dev` starts on #6: fold "no units" and "no buildings" into a combined elimination check (or gate "no units" on also having no remaining production capacity), matching how #6 already correctly gates "no more economy" on both stockpile *and* production buildings.
**Apply when:** Reviewing any future round-based or life-total-based victory/loss condition in this project — check whether a resource/production-carryover mechanic exists that could put a faction in a legitimate "temporarily at zero but not actually eliminated" state, and make sure elimination checks account for it rather than triggering on a momentary snapshot.

### 2026-08-18 — Arch — UGUI requires InputSystemUIInputModule in this project, not the default EventSystem module
**Context:** Review of issue #7 (In-Round HUD & Build/Production Menu), the project's first UI system.
**Learning:** `ProjectSettings/ProjectSettings.asset` has `activeInputHandler: 1` — New Input System only, legacy Input Manager fully disabled project-wide. UGUI's default `EventSystem` GameObject ships with `StandaloneInputModule`, which depends on the legacy `Input` class and will not receive any clicks under this setting. `com.unity.inputsystem` (1.19.0, already installed) includes `InputSystemUIInputModule`, which must be used instead. This is a hard prerequisite, not a style preference — without it, every UGUI button in the project silently does nothing.
**Apply when:** Any future issue creates or reviews a Unity `EventSystem` GameObject (menus, HUD, dialogs) — confirm it uses `InputSystemUIInputModule`, not `StandaloneInputModule`.

### 2026-08-18 — Arch — No data model exists yet for "which buildings/units are buildable this mission"
**Context:** Review of issue #7. The spec claimed the build/production menu could source its options from existing `MissionEconomyConfig`/`BuildingDefinition`/`UnitProductionDefinition` with no new fields.
**Learning:** That's false against the actual code — `MissionEconomyConfig` only has `economyRoundDurationSeconds` and `factionStarts` (per-faction starting resources + main building), and `BuildingDefinition` only has a `canProduceUnits` bool, not a list of which units it can produce. Nothing anywhere currently enumerates "buildable this mission" or "producible at this building type." Flagged as required additive fields: `MissionEconomyConfig.buildableBuildings: BuildingDefinition[]` and `BuildingDefinition.producibleUnits: UnitProductionDefinition[]`.
**Apply when:** Specing or reviewing any future build-menu/production-menu/roster-selection UI — don't assume an existing ScriptableObject already lists "the available options for this mission/building" just because the underlying definitions exist; check for the actual enumerable list before drafting the Data Model section.

### 2026-08-18 — Arch — BattleManager doesn't expose *why* a round resolved, only that it did
**Context:** Review of issue #8 (Mission End Screen), which wants to show which victory/loss condition fired (wipeout / economy exhaustion / surrender / objective met).
**Learning:** `BattleManager.Resolve(bool playerWon)` is private and only calls `GameManager.CompleteMission()`/`TriggerGameOver()`; `GameManager.OnGameStateChanged` only carries the new `GameState` enum, with no cause data anywhere. Any future UI or logging that needs to distinguish *why* a round ended requires an additive `VictoryReason`-style enum and a new public event/property on `BattleManager`, set at the same point `Resolve()` fires.
**Apply when:** Specing or reviewing any future feature that needs to know why a Battle Round ended (mission end screen, AI post-mortem logic, analytics) — this data doesn't exist yet and needs the additive `BattleManager` change above before it can be read.

### 2026-08-19 — Arch — Mouse-driven input systems have no shared "who owns the cursor right now" concept
**Context:** Review of issue #10 (Camera Manager). `SelectionController`'s drag-select box is purely cursor-position-driven with no public state exposure (`_isDragging` is private); `CameraManager`'s edge-of-screen pan is also purely cursor-position-driven. Dragging a selection box toward a screen edge would make both fire simultaneously — the camera pans out from under an in-progress drag box.
**Learning:** With `CameraManager` this project now has three systems reading `Mouse.current` position independently (`SelectionController`, `AttackCommand`, `CameraManager`) with no shared priority/ownership concept. For #10 specifically, required a public `SelectionController.IsDragging` accessor + a suppress-while-dragging check in `CameraManager` as a go-condition, rather than a bigger `InputMode` redesign — the interaction is narrow enough (one flag, one check) not to warrant a shared input-arbitration system yet.
**Apply when:** Reviewing or spec'ing any future mouse-position-driven system in this project (a third would make it four) — check for silent simultaneous-firing with `SelectionController`'s drag state and `AttackCommand`'s click resolution before approving. If a fourth such system appears, that's the signal to actually build a shared `InputMode`/priority concept instead of another one-off guard flag.

### 2026-08-19 — Arch — EconomyManager's per-round cleanup must never be extended to resource nodes
**Context:** Review of issue #12 (Minimap), which adds a resource-node registry to `EconomyManager` (mirroring the existing `RegisterBuilding`/`DeregisterBuilding` pattern) so the minimap can enumerate nodes without a scene-wide `FindObjectsByType` call.
**Learning:** `EconomyManager.CleanupExistingState()` already destroys every tracked building and active unit on every fresh Economy Round entry (`InitializeFactionStates()` runs this every time), because those are legitimately per-attempt spawned state. Resource nodes are static, pre-placed map content — never destroyed on round reset, only depleted via `ResourceNode.Extract`/`DrainAll`. A registry living on the same manager as this destructive cleanup method is a real foot-gun: it would be natural (and wrong) for a future pass to "complete the pattern" by sweeping nodes into `CleanupExistingState()` too, wiping the map's resources every Economy Round restart.
**Apply when:** Reviewing or extending `EconomyManager` (or any manager with a per-round/per-attempt reset method) with a new registry — explicitly check and state whether the registered thing is per-attempt state (destroy on reset) or persistent map content (never destroy on reset). Don't assume "it's tracked by the same manager" implies "it's cleaned up the same way."

### 2026-08-19 — Arch — `Health` has no faction/owner reference; any per-faction stat system needs to add one, mirroring `Weapon`
**Context:** Review of issue #14 (Wire Stat Upgrades Into Gameplay), which wants `Health` to read a per-faction max-health multiplier from `TechManager`.
**Learning:** `Health.cs` is a fully generic component — `_maxHealth`, `CurrentHealth`, `IsDead`, no reference back to whatever owns it (`UnitBase`/`BuildingInstance`), and therefore no way to determine which faction's multiplier to query. `Weapon.cs` already solved this exact problem for itself (`_ownerUnit`/`_ownerBuilding` cached in `Awake()`, a computed `OwnerFaction` property) — this is the pattern to copy, not reinvent. Also found: `HarvesterGatherBehavior.Start()` calls both `_unit.Agent.speed = _config.moveSpeed` and `_unit.HealthComponent?.SetMaxHealth(_config.maxHealth)` exactly once at spawn — neither move speed nor max health is read live anywhere afterward, unlike `GatherRate` (read live every gather tick) or `Weapon`'s Damage/Range/FireRate (read live every `Update()`).
**Apply when:** Any future feature needs `Health` to be faction-aware (per-faction damage resistance, faction-specific max-health scaling, etc.) — add the `Weapon`-style owner-reference pattern rather than a one-off. Any future feature needs a *live-updating* unit stat that isn't already read every frame/tick (move speed and max health specifically, today) — budget for adding genuinely new ongoing-update logic, not just "insert a multiplier into an existing read," since no such read currently exists for those two.

### 2026-08-19 — Arch — `ProductionMenuPanel` and `BuildMenuPanel` use different update strategies; a cross-cutting feature (like unlock-gating) needs to fit each panel's actual shape, not a single shared assumption
**Context:** Review of issue #15 (Unit/Building Unlock-Gating), which gates buttons in both panels on the same `TechManager.IsUnlocked` check.
**Learning:** `BuildMenuPanel` builds all buttons once in `Start()` and has an existing per-frame `Update()` pass toggling each button's `interactable` (affordability check) — extending this with an `IsUnlocked` check is a one-line addition. `ProductionMenuPanel` has no equivalent per-frame toggle for its unit buttons at all — buttons are only created/recreated inside `Rebuild()`, gated on the *building set* changing, with no lighter-weight interactable-toggle pass underneath. A cross-cutting feature that assumes both panels work the same way would silently under-implement one of them.
**Apply when:** Specing or reviewing any feature that touches multiple HUD panels assumed to be "basically the same" — check each panel's actual current update strategy individually (`CLAUDE.md`'s HUD panel list doesn't distinguish this) rather than assuming a shared implementation pattern; recommend the *less invasive* of the two panels' existing patterns as the target shape for both, rather than inventing a third approach.

### 2026-08-19 — Arch — Unity's `Tilemap` is a native XY-plane system; this project's ground is XZ, so any Tilemap use needs the same explicit rotation every other flat surface already needs
**Context:** Review of issue #17 (Terrain Tilemap Foundation) — the project's first proposed use of Unity's `Tilemap`/`Grid` components.
**Learning:** `CLAUDE.md`'s "World/camera orientation" convention already establishes that every flat surface/sprite in this project needs an explicit `rotation (90,0,0)` to lie on the XZ ground plane instead of standing upright facing the camera (Unity's default assumption, inherited from typical 2D-XY-plane project setups, is exactly wrong here) — but issue #17's spec didn't mention this for the new `Grid`/`Tilemap` GameObject at all, presumably because `Tilemap` "feels" like established 2D tooling that wouldn't need the same treatment other custom geometry did. It does. Also flagged: this project has already hit "flat geometry silently invisible because it's at/below `Ground`'s `Y=0`" once (the 2026-08-18 ring-occlusion pattern) — a new Tilemap layer needs an explicit, stated Y-offset or sorting-layer mechanism to render above `Ground`, not an implicit assumption.
**Apply when:** Any future spec introduces Unity's `Tilemap`, `SpriteRenderer` on a fresh GameObject, or any other component that assumes a native XY ground plane by default — explicitly require the `rotation (90,0,0)` XZ-alignment convention and an explicit above-`Ground` Y-offset/sorting mechanism in the acceptance criteria, don't let "it's standard Unity tooling" imply it's exempt from this project's established orientation convention.

### 2026-08-21 — Arch — The predicted "fourth mouse-ownership system" arrived: Unit Orders' (#26) left-click arming conflicts with SelectionController
**Context:** Backlog review of issues #21-#27 (fresh `/ba` output from the same session). The 2026-08-19 Camera Manager review already flagged that `SelectionController`, `AttackCommand`, and `CameraManager` independently read `Mouse.current` with no shared ownership concept, and predicted: "if a fourth such system appears, that's the signal to actually build a shared `InputMode`/priority concept."
**Learning:** Issue #26 (Unit Orders) specced Attack-Move/Patrol as: press a hotkey to "arm" the order, then the *next left-click(s)* set the destination. `SelectionController.Update()` unconditionally treats every left-click as its own selection/drag-box logic with zero concept of a pending order elsewhere — so as specced, `A` + left-click would double-fire (issue the order AND trigger a new box-select/reselect). The fix isn't the predicted shared `InputMode` system yet — it's simpler: rebind Attack-Move/Patrol destination-setting to *right-click* instead, which is already `AttackCommand`'s exclusive, established domain (and matches Rally Points' (#23) own right-click design), sidestepping the conflict entirely rather than building new arbitration.
**Apply when:** (a) Reviewing any future spec that adds a "press key, then next click does X" interaction — check which mouse button it uses and whether `SelectionController` (left-click owner) or `AttackCommand` (right-click owner) already exclusively owns that button; a new left-click-consuming mode is a real, not theoretical, bug. (b) If a *third* pending-order-style extension to `AttackCommand`'s right-click resolution shows up after Rally Points and Unit Orders, that's the actual trigger point for building the shared `InputMode` concept — two is still comfortably one-off, per the original 2026-08-19 guidance.

### 2026-08-20 — Arch — `AttackCommand` is the one input-handling system with no `IsPointerOverGameObject()` guard

**Learning:** `CameraManager`, `BuildingPlacement`, and `SelectionController` all guard their input handling with `EventSystem.current.IsPointerOverGameObject()`. `AttackCommand.Update()` does not — its right-click resolution raycasts straight into world space regardless of what's under the cursor on-screen. This has presumably been true since issue #5, just not surfaced because the panels it could click through were smaller/differently placed. Not fixed as part of #19 (out of its stated scope), but flagged for `/dev`'s verification pass and any future issue touching `AttackCommand`.
**Apply when:** Reviewing or extending `AttackCommand`, or any future HUD layout change that grows a panel's screen footprint — check whether `AttackCommand`'s missing guard now overlaps a panel it didn't before. Worth its own small follow-up issue whenever it's confirmed to actually cause a click-through order in practice.

### 2026-08-20 — Arch — `MainBuilding.prefab` has no `Health` component; the "is it damageable" question needed a prefab read, not a script read
**Context:** Review of issue #20 (Main Building Invulnerability). The issue's own Open Question asked whether `MainBuilding` has a `Health` component, unresolved from `/ba`.
**Learning:** `Assets/Prefabs/MainBuilding.prefab` YAML has exactly five components (Transform, MeshFilter, BoxCollider, MeshRenderer, `MainBuilding`) — no `Health` anywhere. `Weapon`'s exclusion of `MainBuilding` from combat isn't just "never added to a scanned collection" (the `/ba` diagnosis), it's also "the component that would even need scanning doesn't exist on the prefab at all." Reading `EconomyManager.cs`'s spawn code alone (`GetComponent<MainBuilding>()`/`AddComponent<MainBuilding>()`) wouldn't have caught this — had to open the actual `.prefab` YAML directly.
**Apply when:** A spec's Open Question is "does prefab X have component Y" — read the actual `.prefab` file (plain YAML, greppable/readable directly) rather than inferring from the spawning script's code, which only shows what's added at runtime, not what's already baked into the asset.

### 2026-08-21 — Arch — `Health`'s owner-resolution pattern needs a new branch every time a new "thing that can have Health" type is introduced — it doesn't generalize automatically
**Context:** Review of issue #28 (Main Building Health & Destructibility, reversing #20), which adds a `Health` component to `MainBuilding` for the first time.
**Learning:** `Health.Awake()` (`Health.cs:50-51`) resolves owner faction by checking exactly two hardcoded types — `GetComponent<UnitBase>()` and `GetComponent<BuildingInstance>()` — with `OwnerFaction` (`Health.cs:41`) silently defaulting to `Faction.Player` if neither exists. This is the same shape flagged in the 2026-08-19 "`Health` has no faction/owner reference" entry, but that entry only fixed it for the two owner types that existed *then*. `MainBuilding` is a third type that can now own a `Health`, and it was never retrofitted into the ternary chain — confirmed via direct read, not a hypothetical. The fix pattern is proven and cheap (cache the new owner-component reference in `Awake()`, extend the `OwnerFaction` getter's fallback chain, read the owner's actual field lazily since components like `MainBuilding.Faction` may be set post-`Awake()` via an explicit `Initialize()` call) — but it has to be done by hand, every time, not assumed to already generalize.
**Apply when:** Any future spec adds `Health` (or any other component with this same "resolve owner type via a hardcoded checklist" shape) to a *new* GameObject type that hasn't had `Health` before — explicitly check `Health.Awake()`'s owner-resolution branches for that type before assuming `OwnerFaction` works correctly, don't infer it from the pattern having been "already generalized" last time it was touched.

### 2026-08-22 — Arch — Zoom-linked camera height dolly is safe for raycasting (orthographic rays are parallel), but this project has no proven way to verify audio output at all
**Context:** Review of issue #33 (Positional & Priority-Aware SFX), which moves the Main Camera's actual height in lockstep with zoom so Unity's native 3D audio distance falloff responds to zoom.
**Learning:** (1) Verified, not just assumed: because `Main Camera` is orthographic, its screen-to-world ray direction is always straight down regardless of camera height — so `SelectionController`/`AttackCommand`'s click-to-ground raycast resolution is unaffected by the new height changes. This is a safe technique to reuse for any future orthographic-camera trick that needs "distance" to mean something for a system (physics/audio) that only cares about literal transform position. (2) `AudioManager.PlaySfx`'s pooled sources are reused across categories, so any future per-category `AudioSource` setting (priority, min/max distance, rolloff) must be reapplied per-play, never assumed to persist from creation. (3) The bigger, unresolved issue: this project's entire established verification method (`memory/PATTERNS.md`'s headless `unity-mcp` `RunCommand` pattern) has only ever proven out game *logic*, never actual audio/visual output — "sounds louder when zoomed in" has no established check path at all.
**Apply when:** (a) Any future spec relies on the orthographic camera's position for a non-rendering system (audio, a future fog-of-war/vision-radius idea, etc.) — the "moving camera height doesn't affect click resolution" finding here is reusable, don't re-derive it. (b) Any future spec with perceptual/audio acceptance criteria — flag the verification-method gap explicitly during `/arch`, and push for criteria `/test` can actually check (component field values, computed formulas) rather than "sounds right," or explicitly hand off to a human playtest pass.

### 2026-08-22 — Arch — Any new persisted per-faction state needs an explicit reset-policy decision against EconomyManager's already-multiple-times-firing reset cycle
**Context:** Review of issue #36 (Fog of War Foundation), which adds a persisted 3-state per-faction "Explored" memory grid — the spec never stated whether this resets on a fresh Economy Round entry or persists for the whole session.
**Learning:** `EconomyManager.InitializeFactionStates()` (`EconomyManager.cs:127`) is not a "runs once at mission start" call — it's confirmed, via issue #34's `TestSetup` double-spawn bug, to fire more than once even during completely normal play (once from `EconomyManager.Start()`'s own unconditional call, again from `TestSetup`'s explicit `StartEconomyRound()`). `ResourceNodes` is the one existing registry deliberately, explicitly exempted from this reset (`EconomyManager.cs:47-50`) — every other tracked collection gets destroyed and rebuilt on each call. Any future system that persists its own per-faction state outside `EconomyManager` (fog memory, and likely future systems like kill counters, scouted-intel logs, etc.) inherits this same ambiguity by default and needs its own explicit stated policy, not an assumption inherited from "it's a separate manager so it's fine."
**Apply when:** Reviewing or spec'ing any future manager that persists per-faction state across a mission (not just fog of war) — explicitly check whether it should reset in lockstep with `EconomyManager.InitializeFactionStates()` (subscribe to the same `GameManager.OnGameStateChanged` transition) or deliberately persist like `ResourceNodes` does, and require the spec to say which, rather than leaving it for `/dev` to guess mid-implementation.

### 2026-08-22 — Arch/Dev — Standing project constraint: never spec or approve `Tilemap`/`TilemapRenderer` for a new visual layer in this project
**Context:** Fog of War's shroud (#36) was built on `Tilemap`, following the precedent of the earlier Terrain layer (#17). A human playtest found it completely invisible; investigation (see `memory/PATTERNS.md`'s 2026-08-22 entry for the full trail) confirmed `Tilemap` data can be perfectly correct while literally nothing renders on screen in this project's actual pipeline — likely because the real URP asset uses a 3D `UniversalRendererData`, not the 2D Renderer `CLAUDE.md`'s own conventions call for. Rebuilt as a plain `MeshRenderer` + custom mesh (matching `Utilities.RingMesh`'s established pattern), which rendered correctly on the first clean attempt.
**Learning:** This is a real, project-specific constraint now, not a one-off implementation bug to route around differently next time. The Terrain layer (#17) itself was never actually re-verified to visually render either, beyond "it looks like a grid pattern in screenshots" — that pattern may in fact be coming from `Ground`'s own `GridGroundMaterial` (a normal opaque `MeshRenderer`), not the Terrain Tilemap at all; this was never conclusively distinguished during this investigation and is worth a real check if the Terrain layer's own tile-painting ever needs to matter for gameplay (e.g., a future terrain-elevation or ground-type system).
**Apply when:** (a) `/arch` reviewing any future spec that proposes a new `Tilemap`/`TilemapRenderer` visual layer in MechTS — flag this directly as a known-broken approach in this project and require a `MeshRenderer`+mesh alternative instead, don't let precedent ("Terrain already uses Tilemap") stand in for actual proof it renders. (b) Before relying on the *existing* Terrain Tilemap layer (#17) for anything gameplay-relevant (a future terrain-type system, ground-based effects) — verify it actually renders via the pixel-readback technique (`memory/PATTERNS.md`, 2026-08-22) rather than assuming the "it looks fine in screenshots" impression is real; it may be `Ground`'s own material carrying that appearance.

### 2026-08-22 — Arch — Fog of War's flat shroud plane and any future tall/elevated geometry will visually interact, unforeseeable at spec time since they shipped in the wrong order
**Context:** Review of issue #35 (Terrain Elevation), which was spec'd *before* Fog of War (#36/#37) shipped. `Vision.FogOfWarRenderer` renders the shroud as a single flat quad at a fixed world Y (`0.05`) covering the whole map.
**Learning:** Any future geometry taller than that fixed height (a `Platform_Tier1`, or anything else with real vertical extent) will have its upper portions sit *above* the fog plane, meaning it can be partially visible poking through the shroud even in genuinely Unexplored territory — the flat-quad shroud approach has no way to occlude something taller than itself. This wasn't a mistake in either spec individually — #35 predates #36's existence, and #36's flat-quad design (itself a pivot away from a broken Tilemap approach, same day) had no reason to consider future elevated geometry. It's a real, standing limitation of the current fog rendering approach: it only convincingly hides content that's roughly ground-height.
**Apply when:** Any future spec introduces geometry with meaningful vertical extent (elevation/cliffs, tall structures, flying units at a real altitude) — check it against Fog of War's flat-shroud height explicitly, don't assume the shroud "just works" the way it does for ground-level content. If this becomes a real recurring problem (not just a first-pass cosmetic gap), the eventual fix is likely a per-object occlusion approach (e.g., tall objects also implementing their own fog-visibility check like units/buildings already do, rather than relying purely on the shroud plane to cover them) rather than trying to make the shroud plane itself taller/3D-aware.

### 2026-08-24 — Arch — `NavMeshBakeUtility`'s single persisted asset only "just works" because baking and the live session are the same act — a second Agent Type needs its own explicit runtime-load path
**Context:** Review of issue #40 (Flying Unit Terrain Crossing), which needs a second, permissive-climb NavMesh Agent Type baked alongside the existing one.
**Learning:** `NavMeshBakeUtility.Bake()` (issue #35) writes one persisted `NavMeshData` asset and loads it via `NavMesh.AddNavMeshData` inside the same Editor-time call. This project has zero runtime NavMesh-loading code anywhere — no `Bootstrapper` step touches NavMesh at all. The existing single-asset setup works today purely because the Bake button and the live session happen to be the same act; it was never actually proven to auto-load on a fresh Editor session or in a build. A second, differently-agent-typed asset makes this latent gap concrete: it needs an explicit load call (most likely `Bootstrapper`-time `NavMesh.AddNavMeshData`) for real Play Mode sessions, which didn't exist as a requirement until a second asset made "how does NavMesh data actually get into a running session" a real question instead of an implicit one.
**Apply when:** Any future spec adds a second persisted NavMesh Agent Type, or otherwise assumes NavMesh data is available at Play Mode start without a bake having just run in the same Editor session — verify (don't assume) how the data actually loads; this project's one working example may be surviving on a coincidence, not a real load path.

### 2026-08-24 — Arch — `ProductionMenuPanel` is hard-typed to `List<BuildingInstance>`, not just "doesn't know about MainBuilding" — a real distinction for any future MainBuilding-facing UI change
**Context:** Review of issue #41 (Harvesters Buildable from the Main Building), which needs `ProductionMenuPanel` to also show the Main Building's production queue.
**Learning:** Read the file directly rather than trusting the issue's "needs to read from `EconomyManager.MainBuildings` in addition to its existing `Buildings` list" framing: `_trackedBuildings`, `SameBuildings`, and `Rebuild` are all typed to `List<BuildingInstance>` specifically, not some looser "production host" concept. Showing MainBuilding's queue isn't an additional read alongside the existing one — it requires widening the panel's core tracked-entity type (to `IProductionHost` from #41's own new interface, or a parallel MainBuilding-specific tracking path). This is the same class of gap as the 2026-08-19 `ProductionMenuPanel`/`BuildMenuPanel` update-strategy entry — a panel's stated behavior in a spec can understate the actual type-level rework needed once you read the real file.
**Apply when:** Any future spec touches `ProductionMenuPanel` (or names it as something to "also handle" a new entity type) — check its actual field/method type signatures before scoping the change as small; `List<BuildingInstance>`-typed tracking doesn't take a `MainBuilding` without a real type-level change.

### 2026-08-24 — Arch — Building registration and power/vision contribution happen at the exact same moment today (`BuildingInstance.Start()`); any "under construction, not yet functional" state needs to split them
**Context:** Review of issue #42 (Crewman Build & Repair), whose acceptance criteria require a building to exist (selectable, visible) but not yet contribute power or vision while under construction.
**Learning:** Confirmed directly: `BuildingInstance.Start()` calls `_economyManager.RegisterBuilding(this)` unconditionally, and `EconomyManager.RegisterBuilding` applies `PowerCapacity`/`PowerUsed` at that exact call — there is no separate "register for tracking" vs. "apply economic effect" phase anywhere in the current registration flow. Separately, `VisionManager` (`VisionManager.cs:191`) unions vision radius from every entry in `state.Buildings` unconditionally each tick, with no completion-state check. Both of these are real, load-bearing assumptions baked into the current code ("registered building == fully operational building") that #42's construction-time mechanic breaks for the first time in this project's history — no prior feature ever needed a building to exist-but-not-yet-function.
**Apply when:** Any future feature needs a building/unit to exist in a "not yet fully active" state (construction, a power-down/sabotage-adjacent state, a spawn-in delay, etc.) — check every system that reacts to registration (`EconomyManager` power totals, `VisionManager`'s per-tick enumeration, and any future one) individually; none of them currently have a granular "active vs. registered" distinction, so each one needs its own explicit gate, not a single shared flag that automatically propagates.

**Context:** Review of issue #48 (Unit Upkeep System), whose own spec flagged a risk that a negative-from-upkeep stockpile would incorrectly trigger `VictoryConditionChecker`'s `EconomyExhausted` elimination, and proposed fixing it with "a carve-out for negative specifically."
